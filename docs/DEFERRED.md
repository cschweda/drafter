# Deferred

Work that Phase 0 deliberately leaves for later, with the phase it belongs to.

- **Windowed incremental reparse** (Phase 1, only if profiling demands it). `reparse` runs a full parse behind an API that a windowed version could replace without changing callers; see technical design §2.7 for the budget that would trigger it.
- **More title-page layouts** (Phase 3, with the TV, radio, and UK templates). Phase 0 implements `centered-feature` only. Copyright and Notes don't print on it; a layout that wants them can place them.
- **Widow and orphan control for action** (when a template needs it). Action splits wherever the page ends, as §5.3 says; a template could ask for a minimum number of lines on each side, the way speeches have.
- **Clickable links and images in the Markdown preview** (after Phase 1). The preview shows a link's text and an image's description and nothing else, so no address can run and nothing is fetched. Links that open in a new tab (http, https, and mailto only) could follow, as could images from the writer's own files.
- **Headings as scenes in a Markdown document** (after Phase 1). Go to scene is not offered for Markdown; a "Go to heading" built from the same tree as the preview would do the job.
- **Layout shift on a phone's first paint** (after Plan 5). Lighthouse on drafter.dev at v0.3.0 measured CLS 0.15 on mobile (good is under 0.1; performance still 93). Since the fresh look (v0.23.0) the storage warning is a toast and no longer moves anything. What is left is a phone's sample row ("Sample · Start your own") and its Starting text row: they show once the script is read, after the first paint, and push the pane down. It hasn't been measured again since. Reserving their row, or drawing it in the first paint from what the page already knows, would close it. Courier Prime's `font-display` and the render-blocking entry stylesheet are the next small wins.
- **Licence housekeeping** (found by the clean-room audit, 2026-10-27; not clean-room problems): ship a third-party notices file with the web build (minification strips licence comments; dexie's Apache-2.0 text among them); serve Inter Tight's `OFL.txt` beside the font, as Courier Prime's is; add a `LICENSE` file to each `@drafter/*` package before they're published to npm.
- **A stage play from a Markdown outline** (when asked for). New screenplay from this outline makes a screenplay; a play's version would write `##` stubs under `#` acts and its metadata block.
- **Final Draft's own notes** (Plan FD, Phase 2; when the maintainer supplies real `.fdx` files). Real Final Draft notes anchor to ranges of a paragraph's text. Export writes a note on its own line as a `General` paragraph with `DrafterNote="Yes"`, and a note inside a line as `[[…]]` in the text; mapping to Final Draft's anchored notes waits for real files to test against. On import, each `ScriptNote` comes in as a note of its own after the script, headed by its `WriterName` where it has one (`[[Name: …]]`, as a reader's note) and as `[[fdx: Script note: …]]` where it has none: nothing is lost, but no note sits at the text it was attached to. A Final Draft 13 file anchors each note with `Range="start,end"`, a pair of numbers that look like character offsets into the script's text; placing a note there needs that offset model checked against more real files.

## Plan FD: Final Draft files

What Plan FD (v0.11.0) left for later. Final Draft's own anchored notes are the item above.

- **Testing against real Final Draft files** (when the maintainer supplies them; the files are never committed). Import and export were built from the structure description in the technical design and from hand-made fixtures. Real files may use elements, attributes, or orderings the fixtures don't, and a round trip through Final Draft itself has not been tried. Since 2026-10-29 a synthetic test set (`packages/fdx/test/fixtures/realistic/`: a short film, edge cases, a revised draft, a stage play, and a generated 120-page feature) covers the format's structure as the technical design describes it; it was written by hand with original text and invented values, from the element names the technical design documents, without consulting any real `.fdx` file, Final Draft, or converter, so it can't show what Final Draft really writes. One real file has now been checked (2026-10-29: Final Draft 13's own sample script, inspected for its structure only, element and attribute names; nothing from it is in the repository). It settled most of the guesses: a scene's title can also be a child (`AttributedTitle`) as well as the `Title` attribute; the cast, actors, and breakdown tags hold no writing, so ignoring them is right; and it named the settings and data blocks a save carries (now in `IGNORED`). Still guessed: whether a title page's blank line is a paragraph with an empty `<Text>` (import treats one as a gap either way), and whatever other versions of Final Draft, and other writers' files, carry that one sample doesn't. More real files are welcome.
- **Escaping gaps found in review** (2026-10-29; these already existed before the shooting-script fix, and none comes up in Final Draft's own samples).
  - A backslash inside a note at the start of a later line removes the guard on that line, because `firstVisible` finds the note's `\` first. A line can then read as a synopsis, or a speech can fall back to `[[fdx: Character]]`. No text is lost.
  - An unclosed `[[` before the `[[fdx: Scene Heading]]` and `[[fdx: Shot]]` fallback notes closes at that note: `action()`'s fallback path doesn't apply `breakStrays`.
  - A cue that starts with `@`, a heading that starts with `.`, and a transition that starts with `>` each lose that mark.
- **Export of sections as Final Draft outline paragraphs** (a Call for the maintainer). Final Draft 13 writes acts, sequences, and scenes of its outline as `Outline 1 (…)`, `Outline 2 (…)`, and `Outline 3 (…)` paragraphs, which import now reads as `#`, `##`, and `###` sections. Export still writes a section as a `General` paragraph with `DrafterSection`, which Final Draft shows as plain text; writing `Outline N (…)` instead would put Drafter's sections in Final Draft's outline (import would keep reading the old form). The parenthesised label Final Draft expects, and whether `OutlineLevel` must be written too, need a real file made from an export to check. Export also writes `Version="5"`; import accepts any version, 6 included.
- **Beat cards** (Plan F). Final Draft's beat board (`ListItems`, each `ListItem Type="Beat"` with a title and text) comes in as one `[[fdx: Beat, Title: …]]` note per card after the script; Plan F's Beat Board should take them as cards. Their order and colours are not kept.
- **Alternates** (Phase 4, with Drafter's own alternate lines). A Final Draft paragraph with alternate texts comes in with its current text, and each other alternate as `[[fdx: Alternate: …]]` after it; an alternate no paragraph names comes in after the script. Which alternate Final Draft showed (`Current`) is not trusted: the paragraph's own text is.
- **Character arc beats and pictures.** A scene's arc beats come in as `[[fdx: Arc beat, NAME: …]]` notes after its heading, not as anything Drafter's outline knows. A picture in a paragraph is a `[[fdx: Picture]]` note; the image itself (`Images`) is ignored, never pasted into the script.
- **Revisions** (when asked for). Final Draft's revision marks and colors are not read or written. On import a revised run (`RevisionID`) is plain text like any other, the `Revisions` and `LockedPages` blocks are listed as ignored, and an `OMITTED` scene is a forced heading with its number (`.OMITTED #13#`), so locked numbers such as `12A` and `A16` survive but which pages and lines were revised does not.
- **Final Draft's formatting and settings** (when asked for). Page layout, fonts, smart type, headers and footers, and the like are read and listed as ignored on import, and not written on export. Drafter's templates decide the look.
- **Scene Properties beyond the synopsis** (when asked for). A `Summary` (and a scene `Title`) comes in as a synopsis; Final Draft's other scene properties (color, page length, and the like) are attributes import doesn't read.
- **A Final Draft stage play comes in as a screenplay** (when asked for). Drafter reads a section only from its own `DrafterSection` mark, so a stage play made in Final Draft comes in with its `New Act` and `End of Act` paragraphs as action with `[[fdx: New Act]]` and `[[fdx: End of Act]]` notes, its `Scene Heading` scenes (`SCENE 1`) as forced headings, a `General` scene line as a noted action, and stage directions as action. Nothing is lost, and Problems lists the notes, but the writer has to turn the acts and scenes into `#` and `##` sections and choose the stage-play template. Mapping `New Act` to `#` would need the template chosen on import.
- **A Final Draft title page has no keys** (by design; revisit with real files). Import reads it by order and wording: the first centered block is the Title (a subtitle right under it joins it, so `title` is "HABERDASHERY A Play in Two Acts"), a centered `by` or `written by` is the Credit and the block after it the Author, and everything else, a source line, a draft date, contact details, revision dates, goes into one Notes field. A Source or Draft date key is not guessed from wording.
- **Header and footer text is not imported.** `HeaderAndFooter` is a settings block, so text the writer typed into a header or footer in Final Draft (a draft name, a revision line) is left out of the script; it is only named in `ignored`, which the app doesn't show. Bring it in as a note if writers miss it.
- **Styles beyond bold, italic, and underline.** Any other `Style` value on a run, and the font, size, and color attributes on it, are not read: the text comes in plain, in the case it was typed in (a style that strikes text out or shows it in capitals would be lost). A style on a run nested inside another run is lost (its text is kept). Emphasis that Fountain's markers can't write unambiguously, such as an italic phrase that ends in bold italic, comes in plain, as the existing rule says (the words always survive).
- **A visible backslash on some imported lines.** A line from Final Draft that begins with `#`, `=`, `(`, or `~` and would read as another element is written with a `\` in front, because Fountain has no escape for those. It prints, so the writer deletes it, or changes the line.
- **Small gaps in export.** The space before a note at the end of a line is not put back. `writeXml` does not check names or nesting depth (its input is always Drafter's own tree), and an element holding only an empty string does not round-trip.
- **Attribute values on import.** The reader keeps a tab or newline inside an attribute value as typed, where XML would turn it into a space; a scene's `Summary` with a line break is read as two synopsis lines, which is what Drafter's export means by it.
- **Import on the main thread.** Export runs in the export worker; import runs on the main thread, so a worst-case 5 MB file freezes the page for about 1.4 seconds (Plan FD's measure; the imports' own figures are below). Move it into the worker if real files are slow.
- **An import can grow past 5 MB.** Escaping (`\*`, two-space lines, a tab as four spaces, `[[fdx: …]]` notes) makes the Fountain text longer than the file's text, so an adversarial `.fdx` near 5 MB can import as more than 5 MB of script, which Drafter's own 5 MB open limit would refuse once it is saved. Real scripts are far below it.
- **Stray text on an imported title page.** Text written directly in a title-page `Paragraph`, beside its `Text` runs, is not read, and nothing says so. Final Draft doesn't write that shape; body paragraphs keep such text as a `[[fdx: Paragraph text]]` note, and the title page should do the same.
- **Stray text joins its neighbours.** Text written directly in a `Paragraph` between child elements is joined without a space (`a<Text>b</Text>c` keeps `ac`), and stray text inside a speech ends the speech, so the lines after it come in as noted action. Nothing is lost; it only reads oddly, and Final Draft doesn't write that shape.
- **Error offsets.** An `XmlError`'s offset counts characters after line endings are normalized, not in the original file.
- **A shorter `import.ts`.** The importer is about 800 lines; the emphasis writer could move into its own file.
- **The `.deb` file association.** The Linux package installs a system-wide `*.fdx` glob, which may compete with another application's for Open with. Drafter never asks to be the default, but where nothing else claims `.fdx` a file manager may open it in Drafter; `docs/desktop-install-linux.md` says how to change that.
- **Tests.** The round-trip property test runs under the default 5 second limit, which could be tight on a slow CI machine (the large-input tests no longer use a wall-clock budget; see Timing tests under load). The import property checks kinds only when nothing was mapped to a note. The phone-width WebKit accessibility specs time out when six workers run at once (the pages have no axe violations); run fewer workers.

## Plan B: Cards and notes

What Plan B (v0.12.0) leaves for later.

- **The synopsis field inside a card** (the final accessibility pass). Enter on a card opens an `<input>` inside the card's `role="option"` (`SceneCard.vue`), as the Outline puts one inside its `treeitem`. ARIA doesn't allow interactive content inside an option, so screen readers may announce it differently. Check it with NVDA and VoiceOver, and move the field out of the option if they stumble.
- **Timing tests under load** (when it costs a release). A few unit tests time work against a wall clock ("in under a second", "in linear time"), such as parsing, layout, and lint on large inputs. They fail when the machine is busy, for example while an e2e run shares it, and pass on a quiet machine. Run `pnpm test` on its own before trusting such a failure; giving them budgets in CPU time, or a separate suite, would make them steadier. `@drafter/fdx` no longer has any (2026-10-29): its large-input tests time the same work at n and 4n and require growth under 8 times (`packages/fdx/test/scaling.ts`; quadratic work grows about 16 times), with only a 30-second hang guard, and the other packages' timing tests could follow the same pattern.
- **axe on Cards, Notes, and Scene details** (the final accessibility steps). The design's Done-when asks for axe to pass on all three, in both themes at both widths; the maintainer put accessibility work last, so no new axe tests were written. The existing axe specs stay green. Rows (`role="option"`) also hold pointer-only buttons that the pass should look at.
- **Notes for Markdown documents** (Call 8; when the maintainer decides). Design §5.7 says notes work in Markdown, but a Markdown document has no `[[…]]` parse to list, so Plan B shows no Cards, Notes, or Scene details there. A Notes tab for Markdown would need its own reader, and a decision on whether `[[…]]` there is a note or a link.
- **Reply** (Plan G). Plan B shows a reader's replies nested under the person's earlier note, but has no Reply button; it arrives with the reader mode.
- **Storyline labels on cards** (Plan E). Storyline is plain text in Scene details and on the card; names and colors in the metadata block come with storylines.
- **The package layering bend** (Call 1). `@drafter/outline`, `@drafter/lint`, and `@drafter/cm-fountain` now depend on `@drafter/notes`, which reads design §21's "each package depends only on fountain, templates, layout" as a bar on third-party and upward edges. If the maintainer wants it read strictly, the shared text helpers would move into `@drafter/fountain`.
- **`@drafter/notes` details.** The head length limit counts UTF-16 units, not characters. A change that takes a line out can span the notes beside it, and a save runs up to seven parses. Changing a synopsis that has text after a note rewrites only the text before the first note (a Plan A rule). Setup rules compute the note list twice, and `fields.ts` declares its `LABELS` constant after its first use. There is no direct test of the "alone on a line" edge.
- **The Cards and Notes views.** `groupSizes` repeats the grouping in `CardsPane`, `moveUp` and `moveDown` are named for keys rather than rows, and the drop line is drawn on the dragged card itself. Scene details picks a color by focusing a row while the menu is open, `emptyDraft` repeats the shape of `detailsDraft`, and the scene being gone at save time has no test. "Resolve all shown" stays enabled when only resolved notes are shown (it says so). When two notes have the same text, an open menu can sit on the new row after a change; the action still acts on the right note. `check-build.mjs` could look for the new fixture's title.
- **Label completion** (Call 18). A label used earlier in the same multi-line paragraph is not offered, and the open-mark pattern is not anchored to the line's start.

## Plan C: Snapshots and Compare

What Plan C (v0.13.0) leaves for later.

- **axe on History and Compare** (the final accessibility steps). The design's Done-when asks for axe to pass on both, in both themes at both widths; the maintainer put accessibility work last (2026-10-28), so Plan C adds no axe tests and the existing ones stay green. Screen-reader testing of the History list and the Compare marks waits for NVDA and VoiceOver.
- **Side-by-side Compare** (when asked for; Phase 2 design §2). Compare shows the newer version as pages with the older text struck through where lines were removed. Two versions in two columns is not built.
- **Move detection in Compare** (Phase 4, with revision marks). A scene that moved is shown as removed where it was and added where it is, which is what a line diff gives.
- **The snapshot's kind.** A snapshot does not record whether it was taken from a Fountain script or a Markdown document, so Restore and Save as a file use the script's kind now. Only matters if a script's kind can change after a snapshot was taken.
- **History's edges.** Restore does not check whether the script is busy saving; Restore does not mention a known storage failure; a refused Restore still closes History; and the paths where a snapshot vanished since the list was drawn have no tests. `HistoryDialog.vue` is about 900 lines and could be split (the list, the row menu, and Compare's chooser).
- **Compare's edges.** Closing Compare forgets which tab the slot held before; the newer text is parsed twice when a comparison opens; the Changes list names a change by the scene it falls in, and when two removals sit before the same line their gaps overlap; a snapshot's label in the Compare bar has a time but no date.
- **Snapshot timing details.** A clock set back can date a snapshot in the future, and thinning would then keep it as recent. Each take reads the script's whole history about three times, which is fine at hundreds of snapshots. The hour buckets use local time and are off by an hour's worth of grouping across a daylight-saving change. A take for a script that was just removed answers "unchanged". A failed snapshot on save restarts the 10-minute count, on purpose.
- **Diff performance.** `markPages` compares every change with every printed line, which is quadratic in the number of changes; a rewrite of a whole feature has not been timed. The diff's budget tests use cheap input shapes; a scrambled input from a small alphabet would be a harder test.

## Help: About, samples, and updates

What the Help menu's About Drafter, Sample scripts, and Check for updates (after v0.13.0) leave for later.

- **A slow web install says nothing for a minute.** On drafter.dev, Check for updates waits up to 60 seconds for a new service worker it found to install, with only "Checking for updates…" showing, and then calls it an error. A progress line ("Downloading the new version…") would say more.
- **A sample script that can't be stored fails silently.** When the browser's storage is full, opening a sample script makes nothing and says nothing (the command's error is swallowed, as New's is). It should say why, as a failed save does.
- **A sample script stays a sample script.** `sampleScript` stays on the project after the writer edits or saves it, so it never counts as their own document of that kind for the first New's annotated sample. Clearing it on the first edit or save would be more exact.
- **axe on About and Check for updates** (the final accessibility steps).
- **The desktop app's native About box has no Check for updates button.** The in-app About Drafter has one beside the version (fresh-look Task 3b); the native box (shown only when the page can't show its own, and on a Mac with no window) doesn't.

## Plan D: Spellcheck

What Plan D leaves for later.

- **The context-menu key and Shift+F10 on a misspelled word.** They open the browser's menu, as a right-click off a marked word does; Mod-. (Spelling suggestions) is the keyboard's way to the spelling menu. Opening Drafter's menu from them needs a way to tell a keyboard-made `contextmenu` from a pointer's in each browser, and end-to-end tests in each.
- **IBus and the spelling keys on the Linux desktop app.** IBus's emoji hotkey has been Ctrl+. or Ctrl+; in some versions and desktops, which would take Spelling suggestions or Next misspelling before Drafter sees it. Check on the Linux build; the commands are in the palette either way.
- **axe with misspellings on screen and the menu open** (the final accessibility steps). The design's Done-when asks for axe to pass with marks showing and the spelling menu open; the maintainer put accessibility work last (2026-10-28), so Plan D adds no axe tests and the existing ones stay green. Screen-reader testing of the marks (`aria-invalid="spelling"`) and the menu waits for NVDA and VoiceOver.
- **Downloadable dictionary packs** (Phase 4). Drafter bundles US and British English and has no download mechanism. A pack would ship its own licence file and show it; `DictionaryInfo` in `@drafter/spell` is the shape a pack will take. More languages wait for the packs.
- **A list of the script's dictionary to edit in place.** The words are in the metadata block (`dictionary`), where they can be edited as text, and Undo covers an addition; there is no list in the app, as there is for My dictionary in Settings.
- **Licence files for the app's other bundled libraries.** The Third-party licences page covers the spellchecker, its dictionaries, and the two fonts. The app's other libraries (CodeMirror, Vue, Dexie, pdf-lib, and the rest) are not listed there.
- **A browser that blocks module workers never retries.** If `new Worker` throws, there is no checker for the visit and no message beyond the one about the dictionary; it does not try again.
- **A curly apostrophe inside a suggestion's changed letters becomes straight.** A suggestion replaces only the letters that differ; when a curly apostrophe falls inside them, the replacement has a straight one.
- **Spelling status edges.** A rejected `settled()` could leave a stray "Checking spelling…"; the Problems heading may flash "none found" before the worker's state is set.
- **Cache bounds and small costs.** The token cache is bounded by its number of entries, not their size; `isTiny` allocates a regex match for each unit.
- **Duplicated code.** `hasStrayBoneyard` is a copy of `@drafter/notes`' and could move to `@drafter/fountain`; the logic that finds a package's folder is in `sync-assets.mjs`, `licences.test.ts`, and a regex in `docs.spec.ts`; the nspell and is-buffer versions are written in `licences.vue` as well as in the package file (a test checks them); `playwright.config.ts` has a comment about a 3.5 MB precache that is out of date.

## Structure strip

What the Structure strip (v0.15.0, strip design §11) leaves for later.

- **A zoom that scrolls.** The strip always fits the window's width (Call 5), so in a long script a short scene can be a 2 px sliver with no label; its name is still on the block and in the card. A zoom with a horizontal scroll, keeping the cursor's scene in view, would give each scene room.
- **Dragging blocks to reorder.** The strip edits nothing (Call 13); scenes and sections are moved in the Outline and Cards. Dragging would need the Outline's move edits, a keyboard equivalent, and a drop indicator across rows.
- **Storyline rows and "color by"** (Plan E). A row per storyline (a Timeline lane is a strip row filtered to one storyline's scenes) and a choice of coloring by INT/EXT, day or night, or storyline come with storylines themselves, and Plan E decides whether the script map (Phase 2 design §14) is still wanted beside the strip.
- **A phone version.** Below 1024 px the strip and its button are not shown (Call 16); the Outline does the job there. A phone version would need its own layout and touch targets.
- **axe on the strip, in both themes** (the final accessibility steps). The maintainer put accessibility work last (2026-10-28), so the strip adds no axe tests; it is off by default, so the existing ones see no change. Screen-reader testing of the rows, the block names, and `aria-current` waits for NVDA and VoiceOver.
- **Smaller edges, found in review.** The card is not moved back inside the strip when the window is resized while it shows. Right after a load, a strip whose block count matches the previous script's can briefly be drawn with the previous script's layout (the Outline does the same). A strip kept by pages still rebuilds its rows on each parse. No property test asserts that a section row's blocks are in order, and the 2 ms budget test's parse of a 120-page script runs inside Vitest's default 5-second timeout. The placeholder band drawn while a load's index is on its way has no test of its own. A strip kept by pages can stay frozen while a scene prints nothing (zero width reads as the layout lagging); an explicit "layout is for this parse" signal would fix it. Right after a load the blocks are drawn by words, then a moment later by pages (the panes don't move). The strip is still built for a Markdown document or a narrow window while the setting is on, though not drawn. In a Markdown document Ctrl+Alt+O is taken and nothing is said; it could say why, as the button's title does. A block's visible text ("12 INT. KITCHEN - NIGHT") isn't contained in its accessible name ("Scene 12, INT. KITCHEN …"), for the accessibility pass (WCAG 2.5.3). On a Mac with plain Dvorak, ⌘⌥O is the physical O key. Not checked live: whether Chromium reports AltGr for a left Ctrl+Alt on Windows with a German layout (the rule keeps Ctrl+Alt+O either way).
- **The bars above the panes still arrive late.** After a reload, a bar in the shell's top area (the storage warning among them) can appear after the first paint and push the panes, and the strip under it, down about 37 px. It predates the strip (see the layout shift entry above) and is a candidate for a point release.

## Markdown PDF

What the Markdown PDF release (v0.16.0) left for later (Markdown PDF design §12, and its reviews).

- **PDF bookmarks from the headings** (the final accessibility steps; the first to pick up). A document's headings, and a script's scenes, as the PDF's outline, so a reader can jump to them. Cheap: the layout already knows each heading's page and place.
- **Tagged PDF and PDF/UA, for scripts and documents** (the final accessibility steps). Both PDFs are untagged: a screen reader reads their text in the order it is drawn, which is reading order, but hears no headings, lists, or links as such, and a link has no description.
- **Links to headings inside the document** (`#…`). A link to a heading prints as plain text today; it could jump to the heading's page.
- **A list of link addresses for print.** A link's address isn't printed; a printed copy could list the addresses after the text, or as notes.
- **Drawing images.** An image prints as `[Image: …]`, as in the Preview, and nothing is fetched; images from the writer's own files could be drawn.
- **GitHub's tables, strikethrough, task lists, and footnotes** (with the Preview). Neither the Preview nor the PDF reads them; they print as typed.
- **Syntax highlighting in code.** A fence's language is ignored, and code is one color.
- **Fonts for more scripts, and right-to-left and joining scripts.** Inter Tight covers Latin, Greek, Cyrillic, and Vietnamese (Courier Prime, for code, less); anything else prints as `?`, and the toast names it.
- **A running header.** Pages carry only their number at the foot.
- **Justified text and hyphenation.** Text is ragged right, and a soft hyphen is never drawn.
- **`drafter build` for Markdown.** The CLI builds Fountain only; a Markdown document's PDF is made in the app.
- **The subset tag on the embedded fonts' names.** A subset font's name should start with a six-letter tag (`ABCDEF+InterTight-Regular`); Drafter's fonts are embedded under fixed names (`customName`), for the same bytes every time, so they have none. Viewers draw them fine; a tag taken from the glyphs used would keep the bytes the same.
- **Cancel a long export** (when asked for). An 850-page document takes some 20 seconds in the worker; the toast shows its progress and the editor stays usable, but the export can’t be stopped (it would mean ending and remaking the worker, and the fonts it keeps).
- **A list nested thousands deep, in a Markdown PDF** (with Cancel a long export). The Markdown parser takes roughly cubic time on a list nested very deep (some 12 seconds at 800 levels; 3,000 doesn’t finish), and it can’t say how far it is, so the export shows a bar that moves and never ends. Cancel would let the writer stop it; a time limit on the parse, which then says the document is nested too deeply, could come later.
- **The editor on a line of thousands of Markdown marks** (when it bites). A line of five thousand `>` takes the editor seconds per click or key (CodeMirror measuring the marks' layout, in every browser); the Preview now says such a document is nested too deeply, but the Source stays slow on it. Found in the Task 6 review; it was there before.
- **Progress that moves evenly** (cosmetic). The layout's share of a Markdown PDF's bar is counted by blocks, and the first blocks are slower while the width cache warms, so the bar can creep and then jump. Weighting by characters, or by measured time, would smooth it.
- **NVDA's progress-bar beeps** (the screen-reader pass). NVDA beeps as a `role="progressbar"` changes, by default; check in the NVDA and VoiceOver pass whether the toast's bar beeps, and whether that and the quarters said are too much together.
- **The Preview’s “nested too deeply” message, announced** (the screen-reader pass). The Preview says it in a `role="status"` that is drawn (`v-if`) with the message already in it, and some screen readers announce a live region only when its text changes after it is there. Check with NVDA and VoiceOver that it is said; if not, keep the region drawn and set its text.
- **The Markdown parser in a chunk of its own** (when the workers move to `worker.format: 'es'`). The export worker is one file, so the parser's code (some 80 KB of its 1.3 MB) comes with it though only a Markdown PDF runs it.

## Getting a script out the door

What v0.17.0 (out-the-door design §7) leaves for later.

- **Scene numbering that never repeats a written number.** Number every scene keeps a number written in the script (`#4#`) and numbers the rest by their place, so five scenes with `#4#` on the second print 1, 4, 3, 4, 5; the dialog says so. ## Footnotes in Markdown documents

- **Long runs of one nested-list shape parse in quadratic time** (micromark, not Drafter): each time a nested container closes inside another, micromark's document tokenizer copies the whole event list (`EditMap.consume` in `micromark/lib/initialize/document.js`), so an outline of nothing but `- a` / `  - b` takes 0.27 s at 25 KB, 0.95 s at 50 KB, and 3.8 s at 100 KB (and `- - x` lines repeated, 8 s at 100 KB), at depth 2, where the nesting limit can't help. The maintainer's real 49 KB outline (and 4× it, 195 KB) parses in 41 to 91 ms, linearly, so no patch for now (the controller's ruling). The likely fix: splice only the end of the event list there (the exits go just after the last flow chunk, near the end), upstream or as a `pnpm patch`.
- **A note's indent isn't scaled with its type**: a footnote in the PDF is set at 9 pt but keeps the text's 18 pt list indent (`scaled` in `document/layout.ts` scales sizes and spacing, not indents). Cosmetic.

## Drafts and cuts

- **M3: many sections merged into one.** Merging hundreds of Markdown sections into one huge section reports most of them as cuts: each is held only by containment, and past the candidate cap, or with too little of it left in the merged section, it reads as gone. It leans toward keeping, so nothing is lost, but the Cuts list fills.
- **M4: long paragraphs in a big rewrite.** Above `MAX_TOKENS` (2,000 tokens a side), the word-level diff inside a lightly rewritten block falls back to whole lines, so a removal of 12 or more words from inside a very long paragraph in such a block can be missed.
- **Near-identical templated lines.** Paragraphs or scenes that differ only in a number or a name ("Mara counts to 4.", "Mara counts to 5.") read as the same text, so one dropped among several near-identical ones is taken as moved, and dropping several of them can give no cut.
- **M5: Put back with duplicate headings.** Done in Task 4: Put back takes the neighbour nearest the cut's old place (`where.ordinal`).
- **History of this scene from Cuts.** Deleted scenes had a History button (and H) on each scene; Cuts lists cuts without a snapshot to start from, so it has none. A whole scene cut could find its newest snapshot by its text's hash, and open History of this scene there.
- **The history worker's `place` request** (Put back from a snapshot) has no caller since Cuts replaced Deleted scenes; it is kept, tested, for now.
- **A passage put back** goes right after the line it followed (`where.lineAfter`) while that line is still in its scene or section; otherwise at the end of the scene or section. A passage cut from the middle of a line goes back as its own paragraph.
- **The first-run backfill gives up on a script after 3 failed runs** (`MAX_TRIES`: the history worker stopped, or a comparison threw, each time). It logs a warning and marks the script done, so the old snapshots' cuts of that script stay unfound; the snapshots themselves are untouched. A later release could offer to try again.

- **Not in this release (Drafts and Cuts design §10):**
  - **Deleting a draft or a cut.** Neither has Delete: a draft is the writer's milestone, and the Cuts list is a record. A way to hide cuts the writer is done with, kept per script, is for when a long list gets in the way.
  - **Branching** (two lines of drafts from one), and merging them back.
  - **Revision colors and printed marks per draft**, which come with Production (v0.27.0).
  - **A graphical timeline** beyond Draft by draft's list of steps.
  - **Syncing through a cloud service's API.** The files beside the work, synced by the writer's own Dropbox, Google Drive, or OneDrive, are the sync; nothing is uploaded by Drafter.
  - **Drafts for the Workbook** (v0.29.0), which can adopt this when it is built.
- **Pages in the Drafts list and in Draft by draft.** Both count words only (`pages: null`): laying out every draft each time the list is read would cost too much. Caching each draft's page count when it is frozen would add them.
- **A renamed script's files, when it opens as a new script.** When the script keeps its place in Drafter under a new name (a name changed only in case on a Mac, say), Drafter says so once and writes the full set under the new name (v0.24.0). But a script renamed outside Drafter and opened again from its new name is a new script, holding no drafts of its own, so the old name's drafts folder is not read and nothing is said (Drafts and Cuts design §4). The desktop app may read only names tied to the script's own, and the browser only the granted folder's; finding the old folder by the drafts' own IDs would bring them in.
- **An exclusive create in the browser.** The File System Access API has no create-only-if-new, and `move()` may replace a file of the target's name, so a temp file and a move can't close the gap. Chromium's `create` checks the name is free, writes, and reads the file back: a writer whose text isn't the one left there is told the name is taken and writes `(2)`. One narrow case remains: if the other writer read its file back before this one's write landed over it, its draft is no longer in that file (it is still in its own browser, and is written again after the next Save As). Two tabs of one script can't both write (the tab lock), so this needs two browsers granted the same folder at the same moment.
- **Open Boca instead** (the note bar on a draft file opened itself) opens the work only when this browser or app already has it, and otherwise Open: neither the browser nor the desktop's grants can reach a file beside another by its name alone.
- **Reading a downloaded zip back in.** Export drafts and cuts writes a zip, but Open doesn't read one; on another computer, unzip it beside the script in a folder Drafter can read.
- **A second computer's draft numbers.** Two computers starting a draft at once each take the next number; both are kept (the other as `(2)`), never renumbered. A way to put them in one order is for when it happens.
- **Testing with real synced folders.** Two computers sharing Dropbox, Google Drive, and OneDrive folders were simulated in the desktop e2e (another computer's files written beside the script) and in unit tests, not run on the services themselves.

## Trap documents

What the trap documents (`fixtures/trap/`, 2026-11-01) found that wasn't fixed, because the fix is a judgement call or larger than a fix, and gaps the Security sections don't claim.

- **A NUL byte past the first 8 KB opens** (a decision of 2026-10-26, and a SHOULD of the open spec). Open looks for a NUL in a file's first 8 KB only, so a text file with one later opens with the NUL in the script, and saves it back. The archive imports refuse a NUL anywhere in the script inside. Checking the whole file (at most 5 MB, a fast scan) would make the two agree. Trap: `*-nul-late`.
- **`drafter build` and `drafter check` lay out what Open refuses.** They read any regular file of at most 5 MB as text: one that isn't UTF-8 (each bad byte a U+FFFD), holds NUL bytes, is UTF-16, a PDF, a program, or a web page is laid out as the text it decodes to. Nothing is harmed, since `build` never writes over its input, but refusing them as the app does (`notAScript`, the NUL and UTF-8 checks) would say so instead of printing pages of noise. Traps: `fountain-pdf`, `fountain-exe`, `fountain-utf16le`, and the rest at `cli-build`.
- **A zip entry marked as a symbolic link** is read as its stored bytes, the path it names, which then opens as text (`/etc/passwd` as a one-line script). It is never followed, so nothing outside the archive is read; refusing such an entry outright would be clearer. Traps: `highland-symlink`, `epub-source-symlink`.
- **Memory on a very large file.** A parsed Fountain `Doc` keeps about 40 to 50 times its source: a 5 MB script, the most Open takes, keeps 200 to 270 MB for each parse (measured in Node). Opening a file in the web app parses it about four times outside the editor (`createProject`'s `derive` twice, `firstSceneStart`, `titleFor`), about 110 ms and 200 MB of garbage each at 5 MB. The Markdown parser's tree is larger still for inline HTML: a 2.2 MB table of `<b>` cells kept 171 MB and made 780 MB of garbage in 0.7 s; a 5 MB document of plain lines made about 700 MB. All of it is linear and bounded by the 5 MB cap, but heavy for a phone. Parsing once on open, and a lighter tree, would help. The traps' allowances (`memoryMB`) say where.
- **The desktop app's word for a file between 32 and 64 MB** named on the command line is its own reader's (Highland's, Fade In's, or the export's "over 32 MB"), where the web app says "too big to open (over 32 MB)". Both refuse it.
- **The trap suite in CI.** The desktop workflow's Linux job runs both Vitest parts and the Electron part on every push to `main`; the browser part (`apps/web/e2e/trap.spec.ts`) runs only with the web e2e, which no workflow runs.
- **The content security policy allows inline styles** (`style-src 'self' 'unsafe-inline'`: Vue's style bindings and the editor's need them) and has no Trusted Types (`require-trusted-types-for 'script'`). Neither is a way in today, since no script can run but Drafter's own and the app writes no HTML from text, but both would harden it further.
- **The suite's own `tsconfig.json`** (`fixtures/trap/`) is checked with `npx tsc -p fixtures/trap`, which `pnpm check` doesn't run.
- **The jsdom harness isn't stopped at its limit.** `apps/web/test/trap-open.test.ts` runs the app's real Open (`web-open`, `desktop-open`) in the test's own thread: Vue, the database, and jsdom make a worker impractical, so a trap that never returned there would stall until Vitest's timeout, which can't interrupt synchronous code. Its time and memory are checked after each trap; the same readers run stopped-at-the-limit in `harness.test.ts`, and a few of each kind in real browsers.
- **A `module.json` that is a named pipe** is skipped as "it has no module.json", which is true of what Drafter will read but vague; "its module.json isn’t a file" would say why. Trap: `module-manifest-fifo`.
- **An unknown Final Draft paragraph type comes in whole in its note.** A 1 MB `Type` makes a 1 MB `[[fdx: …]]` note (and a 1 MB name in `mapped`); capping the name a note shows, as Highland's note caps an entry's name at 255 characters, would keep a hostile file from filling the script with it. Trap: `fdx-huge-type`.

## Security audit, 1 November 2026

Known limits the [security audit](security-audit-2026-11-01.md) recorded and that stay as they are for now, with what would change them.

- **HSTS is Netlify's default** (F6, Info). drafter.dev sends `Strict-Transport-Security: max-age=31536000`, which Netlify adds; `_headers` doesn't send one, so there is no `includeSubDomains` and no `preload`. `http://` and `www.` already redirect to `https://drafter.dev/`. Sending HSTS from `apps/web/scripts/csp.mjs` with `includeSubDomains` (and `preload`, once every subdomain is HTTPS-only and the domain is submitted to the preload list) would no longer rest on the host's default.
- **Desktop updates are checked by SHA-512, not by signature** (F8, Info). The AppImage and the Windows installer are checked against the SHA-512 in the release's own feed, which proves the download is intact but not who made it: nothing is signed (Windows is unsigned, and the Mac app is signed ad hoc and not distributed), so authenticity rests on the GitHub account and its release. When the Windows build is signed, or the signed Mac app comes, set the publisher name so electron-updater checks the signature too.
- **What the drop grant still trusts** (F2, fixed in part). Electron gives the main process no drop event for a page, so main trusts the preload's report of a real drop. A renderer compromised below the page could still send one, for any script, Markdown, or text file the writer's account can read (`grants.ts` says so). A dropped file read-only until saved, or a question in main before granting one outside a folder already in use, would narrow it further, at the cost of a dropped script no longer saving in place.
- **Advisories left in tooling** (F3). After Nuxt 4.6.3, `pnpm audit --prod` lists 20 (6 high, 9 moderate, 5 low): `node-forge` (the dev server's self-signed HTTPS, through `listhen`), `glob` and `minimatch` (workbox-build, @vercel/nft, electron-builder), `esbuild` 0.27 (`@nuxt/fonts`), and `deepmerge` (workbox-build). None ships: drafter.dev is static, and they are in the build and the dev server. They go as their parents release fixes, which Dependabot now brings; a pnpm `overrides` entry would take them sooner if the dev server is ever run on a network others can reach.
- **The browser tests on a pull request are shown, not required** (2026-11-01). On GitHub's shared runners the Chromium suite takes about 55 minutes, and 14 tests on macOS and 22 on Linux miss: the timing tests ("no long task", "quickly", "budget", left out on CI now), keyboard and focus timing (`a11y:767`, `element-bar:751`, `strip:327,421`, `history:125`, `app-menu:112`, `compare:223,259,276`, `pane-align:150`, `character-grid:234`), and on Linux the font-width layouts (`element-bar:60,496,532,647`, `script:314`, `settings:359`, `shell:561`, `modules:183`, `sample-modules:223`, `strip:264`). Every one passes on a writer's computer, where the full suite on all five projects is a release gate. To make them required: wait on what a test means rather than on time, and check each Linux layout failure for a real layout bug, since Linux desktop users see those fonts.
