# Decisions

Choices made where the design documents are silent, and contradictions between them, recorded as dated bullets. The technical design wins over the architecture document; the kickoff prompt wins over both for Phase 0.

## Tooling

- **2026-10-25** — Vitest 5 runs one project per package: the root `vitest.config.ts` lists `packages/*`, and each package's own `vitest.config.ts` merges `vitest.shared.ts`. Vitest 5 recommends merging a shared base rather than the root config, because a referenced config that inherits `projects` becomes a container of nested projects.
- **2026-10-25** — Workspace packages resolve to source during development: tests through exact-match aliases in `vitest.shared.ts`, and type-checking through a `source` export condition (`customConditions` in `tsconfig.base.json`). Builds and published packages use `dist/`.
- **2026-10-25** — Biome formats with 2-space indents, single quotes, and 100-column lines. It skips Markdown, which Biome 2.6 now formats and would restyle the design documents, and the generated lockfile. The linter uses `"preset": "recommended"`; `biome migrate` turned the old `"recommended": true` into `"preset": "none"`, which disables every rule.
- **2026-10-25** — tsdown builds with `fixedExtension: false`, so packages ship `index.js` and `index.d.ts` (ESM through `"type": "module"`) rather than `.mjs` and `.d.mts`.
- **2026-10-25** — Vitest 5 made `bench` a test-context fixture; `pnpm bench` runs `vitest bench --run` across the projects.
- **2026-10-25** — Property tests set `size: 'max'` on array arbitraries: fast-check's default size caps generated arrays at about ten items, whatever `maxLength` says.
- **2026-10-25** — Tests compare documents through `toJSON`, because `sem` and `inline` are lazy getters that deep equality doesn't read.

## `@drafter/fountain`

- **2026-10-25** — **Title page detection.** The title page is the first paragraph of the file when every line is a `Key: value` line or an indented continuation, and at least one key is recognized (Title, Credit, Author, Authors, Source, Draft date, Date, Contact, Copyright, Notes). The recognized-key rule keeps an opening `FADE IN:` from reading as a title page. Leading blank lines mean there is no title page.
- **2026-10-25** — **Runs and line-level markers.** A line starting with `#`, `=`, or `===` always starts a new run, so it ends a speech as well as an action paragraph. Within a run, a dialogue group recognizes only parentheticals and `~` lyrics, as §2.5 says.
- **2026-10-25** — **Transparent lines.** Lines that hold only notes or boneyard never start or end a content block. At the start or end of a run they form their own `note` or `boneyard` block, named after the first region they touch; between content lines they belong to the preceding block.
- **2026-10-25** — **Printable text.** `sem.text` and `line.inline` hold the text that prints: markers, notes, boneyard, emphasis markers, and escaping backslashes removed. Action lines keep their leading spaces; every other element is trimmed, as the spec says leading whitespace in non-action elements is ignored.
- **2026-10-25** — **Emphasis matching.** A delimiter run matches only a run of the same marker and the same length: `*`, `**`, or `***` for italic, bold, or both, and a single `_` for underline. Longer runs are literal. A backslash escapes `*`, `_`, and `\`.
- **2026-10-25** — **Character names.** `characters()` groups cues by the name exactly as typed, so `@McCLANE` and `MCCLANE` count as different names. `sem.extension` keeps every parenthetical extension as typed, such as `(V.O.) (CONT'D)`.
- **2026-10-25** — **Scene heading parts.** Location and time split at the last ` - ` or ` – ` (en dash); with neither, `time` is null. A heading prefix must be followed by a period, a space, or the end of the text, so `INTERIOR` is not read as `INT`.
- **2026-10-25** — **Linear time on any input.** Files come from outside and the editor parses on the main thread, so no scan may be super-linear. Cues, title-page keys, and scene numbers are scanned by hand rather than with backtracking regular expressions; a failed search for a note's `]]` is remembered up to the blank line where it stopped; classification finds each run's last content line once; note text uses binary search over the regions; and emphasis keeps one opener stack per delimiter kind, with difference arrays for styles. `test/complexity.test.ts` pins each case.
- **2026-10-25** — **Line endings.** Only `\n` ends a line. A trailing `\r` (CRLF) and a leading byte-order mark are ignored by classification and kept in the raw text; a bare `\r` anywhere else is ordinary text.
- **2026-10-25** — **Regions.** `doc.regions` keeps the pre-pass's result on the document, so the editor can color notes and boneyard without scanning the text again. It lists every closed note and every boneyard, open or closed, in source order, with offsets into the source as everywhere else. An unclosed `[[` stays text and is no region. Nothing is special-cased: a note in a title-page value is a region, and the `/* drafter … */` metadata block is a boneyard. `toJSON` leaves regions out, so `DocJSON` v1 stays what `drafter build --json` writes, and a test that compares documents through `toJSON` has to compare `regions` on its own, as the `reparse` property test does.
- **2026-10-26** — **`setMeta` writes the metadata block as text changes.** It returns `TextChange`s in the old document's offsets, as `reparse` and the editor take them, and does not parse or print. With a readable block, it replaces the boneyard itself, from its `/*` to its `*/`, so the blank lines and indent around it stay byte for byte. With none, it appends at the very end: enough line breaks to leave one blank line, then the block and a final line break (an empty script gets the block alone). A block that is not valid JSON is kept, since its text is the writer's, and a good block is added after it. `parse` reads the last one only, so the good one is the one that counts. The JSON is `{ v, ...rest }` on one line, so `v` comes first and defaults to 1, and `/` is written `\/` throughout. JSON reads that as `/`, and neither a `*/` nor a `/*` can then appear in the block, whatever the values hold. The block's line break is the script's own, the first `\r\n` or `\n` in the source, else `\n`, so a CRLF script stays CRLF. When the existing block's settings equal the new ones, whatever its layout or key order, the result is `[]` and the writer's formatting is left alone.
- **2026-10-26** — **`setMeta` writes nothing after an unclosed boneyard.** When `doc.regions` has an unclosed region, `setMeta` returns `[]`. An appended block's `*/` would close the writer's own `/*`: the template choice would not be read back (`parse().meta` stays `null`), the `unclosed-boneyard` error that tells the writer to close it would go while the rest of the script stayed hidden, and every repeat would append another block. The writer closes the `/*` first, and the error says so.

## `@drafter/templates`

- **2026-10-25** — **Hand-written validation.** The technical design (§4.4) validates templates against a JSON Schema generated from the TypeScript types, but the kickoff allows no runtime dependencies, so a hand-written validator does the same job. It reports every problem with the path to the field, rejects unknown fields (so a typo like `colour` doesn't pass silently), and also checks cross-field rules a schema can't express: roles fit the text column, the grid fits its paper, every rule's role has a style, and every kind reaches a rule without conditions.
- **2026-10-25** — **Loading sets.** `loadTemplate` resolves `extends` against templates that are already loaded, so the only cycle it can see is a template that extends itself. `loadTemplates` loads a set that may extend one another, in dependency order, so cycles such as `a → b → a` are caught. It loads all of the set or none.
- **2026-10-25** — **Defaults and shapes.** Only `keepWithNextLines` (2), `extends`, `lint`, and the page `header` and `footer` are optional. `resolveRole` returns `page_break` for page breaks, which never go through the role map. The built-ins are deep-frozen; extend one to change it.
- **2026-10-25** — **Inch conversion is exact.** A value must convert to a whole number of characters or lines. Floating-point products of these values come out exact in practice (`0.7 × 10` and `⅓ × 6` both do), so there is no rounding tolerance to hide an off-grid value.
- **2026-10-25** — **Stage play details the kickoff leaves open.** Parentheticals are indented 10, 40 wide, and italic; lyrics are indented 10 and italic; act headings take two blank lines before and scene headings one; `(MORE)` sits at column 27, centered under the cue.
- **2026-10-25** — **Heading levels.** A role's `heading` is an integer from 2 to 6. Level 1 is the page's own title, the app's `<h1>`, so the script's headings start at 2. The validator rejects 1, 7, fractions, and strings, naming the field and the allowed levels. Only roles that print as headings carry one: `scene_heading` in the screenplay, and `act_heading` (2) and `scene_heading_play` (3) in the play. Character cues don't, since a feature has about a thousand (technical design §13). Roles merge key by key under `extends`, so a child keeps its parent's marks and can change a level, but can't remove one: `null` is rejected like any other bad level. The layout reads the fields it lays out with and no others, so it ignores `heading`.
- **2026-10-25** — **Lint rule ids are plain strings.** `lint.disable` holds non-empty strings, and the templates package doesn't know the lint rules, so a misspelled id isn't caught here. The stage play turns off `heading-no-time` and `transition-not-last`: it maps scene headings and transitions to `disabled`, so there are no sluglines or transitions to check. A child that extends the play and sets its own `lint.disable` replaces the list, as every array does, and repeats the two to keep them off.

## `@drafter/layout`

- **2026-10-25** — **Line shapes.** A row holding two pieces of text, the two columns of dual dialogue or the contact block and draft date on a title page, keeps the right one in `LayoutLine.right`. Title-page lines are synthetic `title` lines with `blockIndex: -1`, since they come from no block. Blank lines are synthetic `blank` lines with role `blank` and an empty span where they stand in the source. Text the engine adds to a source line, a continued-speech `(CONT'D)` or a role's prefix or suffix, is a run marked `synthetic: true`, so the line still belongs to its block and the property tests can leave the added text out.
- **2026-10-25** — **Characters and case.** One code point takes one column, so a surrogate pair is never split. Tabs become four spaces in every element, not only action. A role's `case` applies to the source text; the template's own strings, `more`, `contd`, `prefix`, and `suffix`, print exactly as the template spells them.
- **2026-10-25** — **Keep-with-next for speeches.** When a heading's chain ends at a speech, the speech must be able to start on the page under its own split rules: whole, or split with `minLinesBefore` and `minLinesAfter` met. §5.3's formula, `min(lines, keepWithNextLines)` plus one for `(MORE)`, agrees with this at the default thresholds of 2 and 2, but with `minLinesAfter: 3` it can keep a heading on a page whose speech then moves whole, stranding the heading. A block that prints only blank lines (two-space lines) can't be what a heading is kept with, so the chain runs on past it.
- **2026-10-26** — **Blank lines that open a block.** §5.3's `min(N's lines, keepWithNextLines)` counts from the first line of N that prints something. Two-space lines at the top of an action block print blank, so a heading kept with only those would end its page with nothing under it. They still share the page with the heading; they just don't count toward the two lines. Blank lines further into a block, including `lineSpacing: 2`'s, still count, as before.
- **2026-10-25** — **Splitting a speech with more than one part.** A speech is one group: cue, then parentheticals, dialogue, and lyrics. It splits only after a dialogue or lyric line, never after a parenthetical or a blank line, and the thresholds count dialogue and lyric lines only. On an empty page, a speech that can't meet the thresholds anywhere (a parenthetical nearly a page long, say) splits at the last place it can; one with no place at all prints what fits and continues without `(MORE)`. A blank line left at the top of a continued speech is dropped.
- **2026-10-25** — **Continued speeches.** Speakers are compared by name, ignoring extensions and case, so `DANNY (V.O.)` continues `DANNY`. A scene is everything between scene-heading blocks, whatever role the template gives them. Two speeches with nothing between them count as continued. A dual pair neither gets nor triggers `(CONT'D)`, even when it's too tall for a page and prints one speech after the other.
- **2026-10-25** — **Dual dialogue details.** A `^` pairs with the previous printed item when that is a speech not already paired; omitted blocks such as notes between the two don't count. In a column, each part wraps to `dual.width` minus its indent, the role's alignment is ignored, and lyrics sit at the dialogue indent. The pair takes the left cue's space before.
- **2026-10-25** — **Disabled and omitted blocks.** A disabled block takes the role and style that action takes in the template, so its lines carry that role; if the template omits action, the disabled block is omitted too. Scene numbers count only the scene headings that print as scene headings, so a play's disabled sluglines get none.
- **2026-10-25** — **The index.** A block that prints nothing maps to the next printed block's first line, a block at the end with nothing printed after it to the last printed line, and when nothing prints at all, to page 1, line 0.
- **2026-10-25** — **Title page (`centered-feature`).** Title, Credit, Author or Authors, and Source print centered in that order, from line 22 of the paper, one blank line between groups; Contact prints bottom left and Draft date (or Date) bottom right, level with the contact block's last line, each wrapped to half the text column so they can't collide. Copyright, Notes, and unknown keys don't print. A title page with nothing to print is left out, and the script still starts on page 1. When the fields don't fit, the centered block moves up, and if they still don't fit, the excess is dropped with a `title-page-overflow` diagnostic.
- **2026-10-25** — **Page furniture.** A page number sits flush with the right margin: its column is the text width minus its length. The template's `header` and `footer` are copied to every body page with `{n}` replaced by the page number. Layout diagnostics are all warnings, listed in document order.
- **2026-10-25** — **Property tests.** "No page starts with a blank line" applies to body pages; the title page is placed, not filled, and starts blank by design. "No character or scene-heading line is the last content line on a page" is tested as no keep-with-next role (cues, headings, parentheticals, act and scene headings) at the foot of a page, except where a forced break or the end of the script ends it.

## `@drafter/render-pdf`

- **2026-10-25** — **Spaces are position.** A run's leading and trailing spaces move the pen instead of being drawn, so every visible character still lands on its column and text extraction doesn't pick up stray spaces. Control characters, which pdf-lib would treat as line breaks, print as spaces, and unpaired surrogates as U+FFFD, each in the column the character took.
- **2026-10-25** — **Fonts.** The caller passes all four Courier Prime styles, and `renderPdf` checks for them up front, but only the styles a script uses are embedded, each as a subset. Each embedded font gets a fixed name, because pdf-lib otherwise tags a subset's name at random.
- **2026-10-25** — **Same input, same bytes.** The document carries no creation or modification date and no random identifiers. Its creator is "Drafter", and its title is the title page's title when there is one.
- **2026-10-25** — **Header and footer.** The template's header prints at column 0 on the page number's line, `numbering.line` from the top edge; the footer prints at column 0 the same distance from the bottom edge. The design gives them no position.
- **2026-10-25** — **An empty layout prints one blank page** at the template's paper size. pdf-lib would add a default page of its own to an empty document, but not at the template's size.

## Tooling, continued

- **2026-10-25** — **Node 22.13 or later.** `pdfjs-dist` 6, used in the PDF tests, requires Node 22.13, and `commander` 15, the CLI's argument parser, requires 22.12. The root `engines` field says 22.13; `.nvmrc` stays `22`, which installs the latest 22.x.

## `@drafter/cli`

- **2026-10-25** — **`build` builds; `check` judges.** `build` prints errors and warnings to standard error and still writes its outputs with exit code 0, since a script with an unclosed boneyard still lays out. `check` prints every diagnostic, notes included, and exits 1 on any error. Diagnostics print as `file:line:column: severity: message [code]`, with columns counted in code points after any byte-order mark, and parse severity `info` printed as `note`.
- **2026-10-25** — **Outputs.** With no output named, `build` writes a PDF beside the input: `script.fountain` becomes `script.pdf`, and any other name gets `.pdf` added, so the default can never be the input itself. An output of `-` goes to standard output, one at most, and no output may be the input file.
- **2026-10-25** — **Template names.** An unknown `--template` id is an error; an unknown template in the metadata block is a warning, and the script falls back to `us-screenplay`, as the app will (technical design §4.5). A name is a built-in only if it's one of the built-ins' own keys, so a metadata block naming `constructor` or `__proto__` gets the fallback, not an inherited object. `--template` reads a file when its value ends in `.json` or contains a path separator. `check` takes `--template` too, since the template changes the page count and layout diagnostics.
- **2026-10-25** — **Fixed-width text.** `--txt` prints each page as the template's full grid, margins included, with page numbers, scene numbers, header, and footer at their columns. Trailing spaces and the blank rows at the foot of each page are left off, and a form feed separates pages. Control characters print as spaces, so the grid stays aligned in a terminal.
- **2026-10-25** — **Nothing raw reaches the terminal.** File names, scripts, and templates can come from anyone, and the CLI echoes parts of them: a template name from a metadata block, a template's name and field names, a JSON parser's excerpt. Every string `run()` prints passes through one filter that shows C0 control characters (except tab, newline, and form feed), DEL, and C1 as `\u001b`-style escapes, rather than each message escaping its own pieces. PDF bytes are refused when standard output is a terminal.
- **2026-10-25** — **Entry points.** The kickoff names `packages/cli/dist/index.js` as the binary, so `src/index.ts` is the executable and `src/cli.ts` the importable entry (`run`), which the package exports and the tests alias to.

## `@drafter/lint`

- **2026-10-25** — **The whole script, every time.** `lint` runs every enabled rule over the whole script on each call and doesn't implement technical design §9's `local` flag, which limits a rule to the edited scene and its neighbors. Every rule is linear in the script's size, and the editor's linter waits 300 ms after typing stops, so limiting a rule to one scene saves nothing yet. `Rule` has no `local` field, and a rule's context carries no `layout`, which §9 also lists, since no Phase 1 rule reads one. A rule that needs either adds it then.
- **2026-10-25** — **Severities.** A rule that carries over a parse diagnostic keeps the severity the parser gave it: `unclosed-region` reports an unclosed boneyard as an error and an unclosed note as a warning, `invalid-meta` is a warning, and the two Strict rules are info. `Rule.severity` is the highest a rule reports, so `unclosed-region` declares `error` even though its notes are warnings. The diagnostic's own `severity` is the one to read.
- **2026-10-25** — **`strict` raises two rules.** `strict` turns the Strict Fountain rules, `heading-blank-after` and `multiline-parenthetical`, from info into warnings, and changes no other rule. The runner does it from the exported `STRICT_RULES`, so the rules never read the option, and the app can use the same list to choose the fixes that "Fix all" applies.
- **2026-10-25** — **Which template settings it reads.** `lint.disable`, together with the `disable` option, and nothing else. `lint.enable` is for rules that are off by default, and Phase 1 has none; `lint.options` waits for the first rule with an option. An id that names no rule changes nothing, and a rule that is off doesn't run.
- **2026-10-25** — **Fixes are lists of text changes in the script's own offsets,** in order and never overlapping, so the editor can send one fix, or every Strict fix together, as a single transaction. A line's span ends with its CRLF's `\r`, and the fixes depend on that. `heading-blank-after` inserts a line break at the end of the heading's text, in front of the `\r`: `\r\n` when the line ends in `\r`, otherwise `\n`, so each heading gets its own line's ending even in a file that mixes them. `multiline-parenthetical` replaces each line break inside the parenthetical with one space, taking with it a `\r` before the break and the spaces and tabs on both sides of it, the line's trailing whitespace and the next line's indent. The trailing whitespace goes too, so it can't leave a gap of several spaces in the joined line. The break after the closing line lies outside the parenthetical and stays as it was.
- **2026-10-25** — **No fix inside a note or a boneyard.** When a heading line's end falls inside a note or a boneyard that runs on to the next line, `heading-blank-after` reports the problem and offers no fix. A blank line inside a note ends the note, so its text would show in the script, and one inside a boneyard leaves the heading with text below it, so every "Fix all" would add another blank line. `multiline-parenthetical` has no such case: it only turns line breaks into spaces, which leaves every note and boneyard in one piece.
- **2026-10-25** — **A cue-like line.** `character-without-dialogue` reads a line as the parser reads a cue (technical design §2.5): a name, then any number of parenthesized extensions, then an optional `^`, and nothing else. The upper-case test applies to the name alone, as in the parser, and not to the whole line: the name has at least one capital letter and no lowercase letters, and the extensions may be in any case. So `HANS (on the radio)` and `BRICK ^` count, and `MARGARET (60s), cardigan buttoned wrong.` doesn't. The parser doesn't export its cue reader, so the rule has its own copy of the grammar, and a test sets the two against each other on generated lines. The line has to be an unforced action block of one line, and two kinds of line are left alone. Forced action (`!MARGARET`) is the writer saying it is action, and the fix would also run two paragraphs into one. A line whose emphasis took effect, or that has a backslash, doesn't print as typed: emphasis markers print as styling, so `*MARGARET (V.O.)*` prints as a cue while the parser, which tests the markers too, reads none, and a fix couldn't turn it into one. Notes and boneyard on the line don't matter, since neither prints and the parser skips both.
- **2026-10-25** — **One blank line, then speech.** The cue-like line counts only if the very next block is an unforced action block with exactly one blank line between them, which is two line breaks in that block's `leading`. As in the parser, a line of spaces or tabs is blank, and a line of exactly two spaces isn't, since it joins a speech. A note or a boneyard between the two is a block of its own, so that pair is not looked at, and neither is a pair with two blank lines. The second block has to look like speech: its first line opens with `(`, or the cue-like line's name is the name of a cue elsewhere in the script, before it or after, with any extension or none. Names are compared as the layout compares them, ignoring case, so a forced `@Margaret` counts for `MARGARET`. Only the first line is checked for the `(`, since below it is the speech itself. A shout such as `BANG!` is reported only if a parenthetical follows it.
- **2026-10-25** — **`character-without-dialogue`'s fix removes the blank line.** *Remove the blank line* deletes the blank line's text and its line break. For an empty line that is the break alone, the second one before the speech: `\n`, or `\r\n` in a CRLF file. Every other line break stays, so a file that mixes endings keeps each one. Spaces and tabs on the blank line go with it. Deleting only the break would run them into the first line of the speech, and when that line is the two-space line that joins a speech, three spaces make a blank line: the cue would stay alone and the problem would still be there. No fix is offered when the blank line holds a carriage return of its own, since removing it would change the file's line endings. The problem is still reported.
- **2026-10-25** — **`manual-contd` reports a typed `(CONT'D)` only where the layout would add one.** Technical design §9 defines the rule as "a typed `(CONT'D)` that the engine would add anyway (§5.4)", so it makes the layout's own decision, as `#entries` in `@drafter/layout` does, and reports a cue whose extension matches the pattern only if the layout gives its speech a continued-speech `(CONT'D)`. That happens when the template's `dialogueSplit.contdAfterAction` is true and the cue's name, trimmed and upper-cased, is the name of the previous dialogue group in the same scene. The speaker is forgotten at each scene heading, but not at a section or a page break. A dual cue (`^`) that pairs with the speech just before it gets none, neither does the speech it pairs with, and after the pair nobody has spoken last. A `^` cue pairs only with a speech that is the latest thing the layout set down and isn't paired already. A page break, a block that prints, or an earlier pair in between leaves the `^` cue to be laid out like any other, and it can be reported. Whether a block prints comes from the template's role map, so a note is no obstacle in `us-screenplay`, where notes are omitted, and action is. The rule is quiet, then, for the first speech in a scene, after someone else's speech, on dual dialogue, and in `stage-play-standard`, whose `contdAfterAction` is false. It doesn't ask about the other place the layout writes a `(CONT'D)`, the cue repeated at the top of the next page when a speech splits, since that depends on where the page breaks fall. The rule copies the layout's logic instead of calling it, and a test lays generated scripts out with `paginate`, in seven templates, and checks that the cues it reports are exactly those whose cue line gets the engine's marker.
- **2026-10-25** — **`manual-contd`'s fix removes every `(CONT'D)` on the cue.** The fix deletes each `(CONT'D)` in the cue's extensions, in any spelling the rule's pattern allows (`(CONTD)`, `(cont’d)`, `( CONT'D )`), together with the spaces and tabs before it, and nothing else. `MARGARET (V.O.) (CONT'D)` becomes `MARGARET (V.O.)`, and a `^`, other extensions, and notes stay where they were. It takes all of them, so one fix settles the problem. No fix is offered when the cue's printed text isn't one stretch of the source, because a note or a boneyard sits inside the cue, so positions in the printed text no longer match the source and a cut could take the note along, or when the cue holds a carriage return of its own, since cutting next to one can join it to a line feed and change the file's line endings. The problem is still reported.
- **2026-10-25** — **`transition-not-last` skips notes, boneyard, synopses, and centered text.** A transition's next block is the first block after it that isn't a `note`, a `boneyard`, a `synopsis`, or `centered` text. The first three print nothing. Centered text is skipped because a transition followed by `> THE END <` (`>FADE OUT.`, then the title) is the most common way a screenplay ends, and a warning there would only nag. The transition passes if that block is a scene heading (a forced one too), a section, or a page break, and is reported otherwise, a second transition included. So action after a title card is still reported: `CUT TO:`, `> TITLE CARD <`, then action. A transition followed by nothing but skipped blocks ends the script and passes, so `>FADE OUT.` before `> THE END <` and the metadata block, which is boneyard, is fine. Forced and unforced transitions are judged the same way.
- **2026-10-25** — **Where the four point, and what they fix.** Each reports the line it is about, with the parser's span, so in a CRLF file the span ends with the line's `\r`, as `heading-blank-after`'s does: the cue-like line, the cue, the scene heading, the transition. `character-without-dialogue` and `manual-contd` offer fixes. `heading-no-time` and `transition-not-last` offer none, since what to write instead is the writer's call. `heading-no-time` reports every heading that isn't forced and has no time after its last ` - `, including an `EST.` heading and the one-line `INT is short for interior.` that the spec reads as a heading. Both are off in `stage-play-standard`.
- **2026-10-25** — **`similar-names` reports each pair once, at the rarer name.** A pair of names one edit apart is one info diagnostic, with no fix, at the first cue line of the rarer name, and its message names the other: `"MARGERET" is one letter from "MARGARET", which has 12 cues. A typo?`. The rarer name is the one with fewer cues. On a tie it is the one that first appears later in the script, since that is the one written after the name it may be a typo of. A name that is rare beside two others is reported once for each, at the same line, in the order the others first appear. The span is the cue line the parser gives, so in a CRLF file it ends with the line's `\r`, as the other rules' do. The message says `1 cue` and `2 cues`, not `1 cues`. Which spelling is right is the writer's call, so there is nothing to fix.
- **2026-10-25** — **Names are compared in upper case, and their cues add up.** `characters(doc)` keys a name as typed, so it lists `@McCLANE` and `MCCLANE` apart. The rule trims and upper-cases each name and adds the counts of those that match, so the two are one name that is never reported against itself, and the cues of both count toward the test that one of a pair is cued at most twice. A name typed two ways is reported at the first cue of either. An extension such as `(V.O.)` and the dual marker `^` are no part of a name, as in `characters`. Messages show the upper-case name.
- **2026-10-25** — **"At least five letters" counts letters.** Technical design §9 asks for names of at least five letters. The rule counts Unicode letters in the upper-cased name, not characters: digits, spaces, hyphens, and punctuation don't count. So `NAME12` and `NAME13`, `COP 1` and `COP 2`, and `R2-D2` and `R2-B2` are never compared, while `LEILA` and `LAILA` (exactly five) are, and `LEILA` and `LEIA` (one name of four) aren't. Numbered names of five letters or more, such as `GUARD 1` and `GUARD 2`, are not left out by this, but by the rule that follows.
- **2026-10-25** — **Names that differ only in their digits are never reported.** Numbered characters (`GUARD 1` and `GUARD 2`, `GUARD 12` and `GUARD 2`) are deliberate, and a typo almost never changes only a digit, so `similar-names` compares the two names with every decimal digit left out, and skips the pair when what is left is the same. A digit is `\p{Nd}`, not `\d`: the digits of other scripts count too (Arabic-Indic, fullwidth), since `\d` is only 0 to 9. Whatever the edit was, a digit changed, added, left out, or swapped with its neighbour, the pair is spared. Anything else that differs is still a typo, a space included: `AGENT 47` beside `AGENT47` is reported, because the space is not a digit. The check follows the edit test, so it runs on a pair that is already one edit apart and costs a pass over its two names: the rule stays linear. Technical design §9 has no such control and leaves a numbered cast to **Mark as distinct**, a pair at a time; with no check, eight guards numbered `GUARD 1` to `GUARD 8`, each cued once, would have been 28 reports. A test lints `GUARD 1` to `GUARD 20000`, which gave 8,001 reports before the check, and finds none, in under a second.
- **2026-10-25** — **`meta.distinctNames` holds the pairs marked as distinct.** It is a list of pairs of names in the metadata block (technical design §8.6), such as `[["MARGARET", "MARGERET"]]`. A pair listed there is never reported, in either order and in any case, since each name is trimmed and upper-cased the way the rule's own names are. `doc.meta` is whatever JSON the file held, so the rule reads it defensively and never throws: a value that isn't a list is ignored, and so is any item in it that isn't a list of exactly two strings, while the valid pairs around it still count. A pair that names a name the script doesn't cue changes nothing. The rule only reads the list; the editor's **Mark as distinct** will write it.
- **2026-10-25** — **Candidate pairs come from an index of one-deletion keys.** Comparing every name with every other takes time in the square of the number of names. Instead each name goes into a map under its own letters and under its letters with any one code point left out, and names that share a key are the candidates, each checked once with `withinOneEdit`. Two names one edit apart always share a key: a changed letter, two swapped neighbours, and a missing letter each leave the same text when the right code point is left out. So nothing is missed, and the work grows with the number of names and the length of each, not with the square of their number. A pair can share more than one key (swapped neighbours share two) and is still checked once. `withinOneEdit` counts code points, and so does the index: a character outside the Basic Multilingual Plane, which takes two UTF-16 units, is one edit, not two. Technical design §9 says Damerau-Levenshtein of at most 1, and at a distance of one the restricted form and the unrestricted one agree, so `withinOneEdit` needs no table: it finds where the names first differ and checks that what follows is what one edit would leave.
- **2026-10-25** — **Two limits keep a hostile file from slowing it or flooding the report.** The index holds a key for each code point of a name, each nearly as long as the name, so one cue of a hundred thousand letters would need a hundred thousand keys of that length. And a file of twenty thousand names that differ in one place would have two hundred million pairs to report. So a name of more than 32 code points isn't compared, and a key that more than eight names share isn't looked at. The second limit has a use of its own: `SOLDIER A` to `SOLDIER I` are a series the writer meant, and nobody makes nine typos of one name. A series of eight or fewer is still compared, and reported where one of them is rare. (A numbered series, `SOLDIER 1` to `SOLDIER 9`, is spared by the digits rule whatever its size.) Tests lint twenty thousand names of 32 letters, twenty thousand that differ only in their last letter, and two cues of two hundred thousand letters each, every one in under a second.
- **2026-10-26** — **`similar-names` skips a pair whose one edit falls inside a short word.** `MR. SMITH` and `MRS. SMITH`, `JOHN JR.` and `JOHN SR.`, and `GUARD A` and `GUARD B` are different people, and the short word is what tells them apart. So after the digits rule, the rule finds the edit as the text between what the two names share at the start and at the end, and spares the pair if that text overlaps a word of three letters or fewer in either name. A word is a run of characters without whitespace, and its length counts letters, so `JR.` has two and `MRS.` three. `MARIO` and `MARIA` (a five-letter word), and `OFFICER DAVID` and `OFFICER DAVIS`, are still reported. A space put in or taken out lies in no word, so `AGENT 47` beside `AGENT47` is still reported. The check runs on pairs already one edit apart, so the rule stays linear. The series limit still stands (nine names that differ in one place are left alone), but its tests use names that differ inside a long word, since `SOLDIER A` to `SOLDIER H` are now spared before they are counted.
- **2026-10-26** — **The fix, *Mark as distinct*, goes through `setMeta`.** Each `similar-names` diagnostic has a fix that adds the pair, in upper case and in the order the message names them (the rarer name first), to `meta.distinctNames`, as the changes `setMeta` writes. The pairs already listed stay, even ones the rule cannot read, and the rest of the block is kept. Only a `distinctNames` that is not a list is replaced, since there is nothing in it to keep. After the fix the pair is listed, and the rule reports nothing for it. The fixes of a script's diagnostics all change the same block, so they cannot be applied together: the editor applies one and lints again, which finds the others still there.

## `@drafter/render-html`

- **2026-10-25** — **Absolutely positioned lines.** Each line that prints is its own element, set at `--row` and `--col` with the margins counted in, instead of a row of padded text. Blank lines aren't rendered: they hold nothing to see or to read, and leaving them out keeps the DOM to what prints. Technical design §6.1 sketches `padding-left` for the column. Absolute positioning also puts a row's two parts, and the page number and scene numbers in the margins, with the same two variables, and a line's own columns can't shift the lines around it.
- **2026-10-25** — **A row's right part reads after the left lines of its run.** The `right` part of a row, the right column of dual dialogue, is a line of its own, and it comes after the left lines of the run of rows it belongs to, so a screen reader reads dual dialogue's left speech whole and then the right one. When the left column is the longer, its last lines stand alone on their rows, and the run goes on through them: a left-only line belongs to the run while its block comes before the right column's first block, and the first line from a later block ends it. When the right column is the longer, its extra rows have a blank left part, which isn't drawn. A title page is not read this way (see the next entry).
- **2026-10-25** — **A title page is read field by field, in source order.** Every line of a title page is from no block (`blockIndex` is -1), so the runs above, which tell the two columns apart by block, can't work on it, and reading it by rows wove a draft date that wraps into the contact block it stands beside: `Jane Writer`, `Revised Draft - January 15,`, `jane@example.com`, `2026`. A date longer than the contact block was worse, since the layout stores its first lines as the rows' own lines, ahead of the contact block's. So a page whose lines are title lines (`synthetic` is `'title'`) is read in a stable sort of all its parts, right parts included, by where each starts in the source (`span.from`). A field's lines have rising spans and no two fields' spans meet, so every field stays whole: a wrapped date follows the whole contact block, and a longer date reads in order. The fields read in the order the writer gave them, which is not always the order they stand on the page: `Draft date:` before `Contact:`, as the Fountain spec's example has it, reads the date first, and `Author:` before `Title:` reads the author first. Reading them as they stand (the centered fields from the top, then the contact block, then the date) would need the layout's names for its title-page slots, which are not part of its contract. Every other page is read as before.
- **2026-10-25** — **Speech groups are found by role.** A group opens at a line whose role is a cue role, takes the lines after it that have a speech role, and ends with a `(MORE)` line. `speechRoles` reads the roles from the role map: those any rule gives `character` blocks (cues) and `parenthetical`, `dialogue`, and `lyric` blocks (speech), whatever the rule's `names`, `depth`, or `afterRole`, and never `omit` or `disabled`, which aren't roles. The cue the layout repeats at the top of the next page when a speech splits is a cue-role line of its own, so it opens the group there: `MARGARET (CONT'D)`. A layout line carries a role and not its block's kind, so roles are all there is to go by.
- **2026-10-25** — **A speech is named by every line of its cue.** `aria-labelledby` lists the id of each line of the cue, not just the first, since a long name wraps and a label that stopped at the first line would stop mid-name: `THE OLD MAN WHO LIVES NEXT DOOR (V.O.)` is two lines in a 33-column cue. The ids count cue lines on the page, `drafter-cue-<page>-<n>`, and not rows, because dual dialogue's two cues share a row. The ids are joined once, when the cue is done, so a cue costs no more than its length.
- **2026-10-25** — **What is hidden from screen readers.** `(MORE)` lines and the furniture (the page number, scene numbers, header, and footer) are `aria-hidden`. Everything else is read, the repeated `(CONT'D)` cue included, since it says who is still talking and names the group. The furniture has no `data-from`, so a click on it goes nowhere. `(MORE)` keeps its span, which is empty, at the place the speech splits.
- **2026-10-25** — **Headings are blocks.** `role="heading"` and `aria-level` go on the block's own element, which holds all the block's lines, so a heading that wraps is one heading with one name. A line with no block (the title page, `(MORE)`, a repeated cue) is never a heading.
- **2026-10-25** — **The furniture stands where the text export puts it.** The page number is on row `numbering.line`, `margin.left + pageNumber.col` columns in; scene numbers are on `margin.top` plus their body row, at `margin.left + sceneNumbers.left` and `.right`; the header is on the page number's row, at `margin.left`; and the footer is on row `height − 1 − numbering.line`, also at `margin.left`. So the screen, the PDF, and the text export agree. The furniture comes after the page's text in the DOM.
- **2026-10-25** — **Control characters print as spaces.** C0, DEL, C1, and the Unicode line and paragraph separators each become a space in their own column, as in the PDF and the text export. A browser draws a control character at the wrong width, which shifts the rest of its line off the grid: Chrome gives a form feed, a carriage return, and DEL no width at all, a bell and a vertical tab a sliver of a column, and a C1 character a fallback glyph wider than one.
- **2026-10-25** — **Role names are free text,** so `role-<role>` turns a space in a role name into a hyphen. Left alone it would make two classes, and `classList.add` throws on one.
- **2026-10-25** — **A page is unchanged when its JSON and the template's are.** `update` compares each page, as JSON, with the page drawn at the same position last time. An equal page keeps its element, so text the reader has selected in it stays selected; a changed page is built apart from the document and takes the old one's place in a single step, and a page past the end of the old layout is added at the end. The template is compared too, as JSON, once for the whole update. A page's DOM comes from the template as well as from the page: heading levels, margins, the scene-number columns, the header and footer rows, the page size, and which roles make a speech are not in the page's JSON, and the layout ignores some of them (`heading`, for one). So any difference in the template draws every page again, and a new copy of an equal template changes nothing. A page's JSON holds its lines' source offsets and block numbers, which an edit that changes the script's length moves on every page after it, and a click reports the offsets. Those pages are patched, not built again (next entry). Pages are matched by position; their numbers are in the JSON.
- **2026-10-25** — **A page that only moved is patched.** An edit that changes the script's length moves every offset on every later page, which changes its JSON, and building all those pages again at each keystroke made typing in a long script slower than it had to be. In Chrome 156, on a script of 121 pages, an edit on page 1 took 19 ms with layout counted when the pages were built again, and 2 ms when they were patched (the reviewer's figures were 21 ms and 87 ms with the CPU slowed four times, against about 4 ms and 14 ms patched). When a page's JSON differs and the template is the same, `shiftOf` walks the old and the new page in step and finds out whether they are the same except that every `span` (of lines, runs, and right parts) moved by one common offset and every `blockIndex` of 0 or more by one common amount. A synthetic line's -1 has to stay -1, and a block can't move below 0, since it would stop being a block. If so, the page keeps its element, and the amounts are added to `data-from` and `data-to` on its lines and `data-block` on its blocks. Those are the only places the DOM holds an offset or a block number, no CSS selects on them, and the grouping and reading order only compare block numbers with each other, which a move by one amount doesn't change. A test builds each page of a script with every kind of line (a title page, dual dialogue, a speech split with (MORE) and (CONT'D), scene numbers, a header and footer), patches it, and expects the page built from the moved source. Any other difference, or a move that isn't the same everywhere, builds the page as before. That is the page that was edited; a page with an edit inside a note on it, which moves the text after the note and not the text before it; and a page that opens with the cue the layout repeats as (CONT'D) when the edit is between that cue and the page, since the repeated cue stands where the original cue did, on an earlier page. Everything the layout emits is compared, one way or the other, since the DOM is built from all of it: a test changes each field of each line, run, and page in turn and expects `shiftOf` to refuse, so a field the layout adds later can't be ignored in silence. The pages are patched after all the new ones are built, so a build that fails still leaves the view as it was.
- **2026-10-25** — **What counts as the reader scrolling.** A turn of the wheel, a `touchstart` or `touchmove`, or a `keydown` of PageUp, PageDown, Home, End, an arrow key, or Space, on the container or anything in it. Each one starts a quiet time of 2,000 ms again, measured by `options.now` (`performance.now()` by default), and `reveal` does nothing until it is over; at exactly 2,000 ms it is over, and before any scroll there is no quiet time. Not counted: any other key, a click, the view's own `reveal`, and the `scroll` event, which the browser fires for the reader's scrolling and for `scrollIntoView`'s alike, so it can't tell whose it is. Dragging a scrollbar is missed too, since it makes no wheel, touch, or key event for the container to hear, so the next cursor move pulls the view back. A key counts whatever modifiers are held and whether or not there was anything to scroll: taking a key press for scrolling errs toward leaving the view where it is.
- **2026-10-25** — **`reveal` picks the line by its row and the page by its number.** `layout.index[b]` is `{ page, line }`. `page` is a page number, with the title page 0, which is the `data-page` of the page's element, and not a position in `layout.pages`; the two differ when a script has no title page, where page 1 is `pages[0]`. `line` counts from the first body row, so the row to look for is `margin.top + line`. `reveal` takes the line with the smallest `--row` at or after that row among those with a `data-from`, so never the furniture, and when two stand on one row it takes the first in the DOM, which is the left one. It doesn't take the first line after the row in the DOM, since the DOM holds the reading order, in which a right column's row can come after left lines of later rows; and it asks for lines at or after the row because blank lines aren't drawn, so a row can hold none. The call is `scrollIntoView({ block: 'nearest' })` as the brief gives it, which moves the least it takes to show the line and leaves a line already in view where it is. `reveal` does nothing for a block the drawn layout doesn't have, for a page that isn't drawn, for a row with no line at or after it, and before the first render. It reads the layout last drawn, not one that `update` is still waiting to draw.
- **2026-10-25** — **A failed font load doesn't blank the pane, and the newest update wins.** The first `update` waits for `fontsReady`. If it rejects, the pages are drawn anyway, in whatever monospace font the browser has, whose advance is nearly always 0.6 em, as Courier Prime's is: a pane that never draws is worse than one a fraction of a column off. The view attaches its handlers to `fontsReady` when it is created, so a load that fails before the first `update` leaves no unhandled rejection. Once the wait is over, `update` draws before it returns, and with no `fontsReady` it never waits, so the app can `update` and `reveal` in one turn. A call that was waiting when a newer one came draws nothing and resolves; the newest call draws, however the two interleave with the end of the wait. After `destroy`, `update` and `reveal` do nothing, and an `update` that was waiting draws nothing.
- **2026-10-25** — **A click reports where its line starts.** One listener on the region handles a click on a line or on a run in it, and dispatches `GOTO_EVENT` from the region, bubbling, with the line's `data-from` as `detail.offset`. The second line of a wrapped line reports where it starts, in the middle of a source line. `(MORE)` reports the place the speech splits, since its span is empty there. The furniture, the paper, and the gaps between lines report nothing. A click that ends a drag across text inside one line is still a click and reports; the view doesn't look at the selection.
- **2026-10-25** — **jsdom 29, not 30.** The DOM tests run in jsdom 29.1, since jsdom 30 needs Node 22.22.2 and the repository supports Node 22.13 and later. `@types/jsdom` is the 28 series, the newest that isn't jsdom 30's, since there is no 29 series.

## `@drafter/cm-fountain`

- **2026-10-25** — **The parser reads the text joined with line feeds.** CodeMirror counts every line break as one position, whatever the file used: `\r\n`, a lone `\r`, or a separator the app sets with `EditorState.lineSeparator`. `state.doc.toString()` joins the lines with `\n`, so `parsedDoc` parses that string, and the parser's offsets are CodeMirror's positions with no translation anywhere in the editor. The parser's CRLF handling matters only when an app's separator leaves a `\r` inside a line, and then a span ends where CodeMirror's line does, `\r` included. Each transaction's changes reach `reparse` through `changes.iterChanges`, with `inserted.toString()`: they come in the old document's positions, sorted and never overlapping, with ranges that touch joined, which is what `reparse` takes.
- **2026-10-25** — **`fountainHighlighting()` brings `parsedDoc`.** The plugin reads the field, so the extension lists it, and a state can have the highlighting without adding the field first. CodeMirror ignores an extension it is given twice, so `fountain()` can list both.
- **2026-10-25** — **Blocks are found by binary search, not `blockAt`.** The task names `blockAt` for finding the blocks that touch a range. But a range most often starts in the gap before a block, on a blank line, where `blockAt` returns `null`, so the first block to decorate has to be searched for anyway. One lower-bound search finds the first block, line, title field, and note or boneyard that reaches a range, and the work after it follows what the range holds.
- **2026-10-25** — **Whole lines of the ranges, and only those.** `fountainDecorations` widens each range to whole lines, since a line decoration belongs at a line's start and a mark can't be cut off, and merges ranges that share a line. A range wholly outside the text, or one that runs backwards, decorates nothing, and one that runs off an end is cut there. A block that runs far past the range, such as a boneyard of thousands of lines, is decorated for its lines in the range only. A note's or boneyard's mark covers the whole region even when the range shows part of it, once, however many ranges it touches. CodeMirror draws only the lines in view, so a mark that runs on costs nothing.
- **2026-10-25** — **CodeMirror sorts the decorations.** They are collected and given to `Decoration.set(ranges, true)`, which checks the order first and sorts only if it must. They come nearly in order, a line decoration and then the marks in the line, line by line, and only the notes' and boneyard's marks start out of place, so the sort stays cheap even for a long run of lines. Building them in order for `RangeSetBuilder` would mean merging the regions into each line's marks by hand.
- **2026-10-25** — **Each style is a mark of its own.** A bold italic run has two marks over the same text, `cm-f-b` and `cm-f-i`, and not one mark with both classes, so a theme can style each alone and a test can ask for one class. The marks are per run, not joined across runs: the emphasis markers between two runs of one style are dimmed, and not styled.
- **2026-10-25** — **`cm-f-marker` is every character a line doesn't print, except whitespace.** A character gets it if it is in no run's printed text, in no note or boneyard, and in no title key, and isn't whitespace as the parser trims it (`\s`, which includes the byte-order mark and a CRLF's `\r`). Characters next to each other are one mark. So `INT. HALL - DAY #12#` dims `#12#` and not the space before it, `**bold**` dims each `**`, and a dual cue's `^` is dimmed without the space before it. The task's table is followed and not technical design §3.2's list: the `[[`, `]]`, `/*`, and `*/` belong to the note's or boneyard's own mark, `cm-f-note` or `cm-f-boneyard`, and are not also markers.
- **2026-10-25** — **A run's span holds characters it doesn't print.** A run's span goes from its first printed character to its last, so it holds what the parser left out in between: the backslash of an escape (`a \* b` is one run), a note, and the delimiters of emphasis inside emphasis of the same style (`*a *b* c*` is one italic run). Escapes and delimiters are markers too, so the extension lines the run's text up against its span. Escapes are found as the parser finds them, left to right, with the run's first character always printed, and the text is then matched from the end: a `*` or `_` that isn't the next character of the text is a delimiter that was taken out. If a run doesn't line up, it counts as all printed and nothing in it is dimmed. When two identical delimiters stand side by side and one of them was taken out, the one that is dimmed may not be the one the parser dropped. A test checks every generated script, and strings of the characters that mean something, for the rule that each character that isn't whitespace is printed, in a note or boneyard, a key, or a marker, and a list of strings that once broke the alignment is checked the same way.
- **2026-10-25** — **The title page.** Every line of it has `cm-f-title`, continuation lines too, and the first line of each field has `cm-f-title-key` over its `Key:`, from the key's first character through the colon. That is not always the field's span start: the key follows a byte-order mark at the start of the text, and a note before it, so the mark is placed by reading the line, and a space before the colon (`Title : Name`) is part of it. A field's runs have one list for each line that holds a value, so a line is matched to its runs by position. Values get the same style marks and markers as any other line.
- **2026-10-25** — **The plugin rebuilds on `viewportChanged`.** `fountainHighlighting` builds its decorations for `view.visibleRanges`, the part of the viewport that is drawn, and builds them again when the text changes or `viewportChanged` is set. CodeMirror sets that flag when the visible ranges change as well as the viewport, which a fold does without moving the viewport (in jsdom, at least), so an unfold rebuilds them too. Without it, what an unfold shows again would have no decorations if the text was edited while it was folded. A test in jsdom folds, edits, and unfolds. jsdom has no layout, so the view's viewport there is whatever CodeMirror estimates, the whole of a short script, and which ranges a real window shows can only be seen in a browser.
- **2026-10-25** — **CodeMirror at its current releases, all five from the start.** `@codemirror/state` 6.7.6, `view` 6.43.15, `language` 6.13.1, `autocomplete` 6.20.4, and `lint` 6.9.7, each with a caret range. None declares an `engines` field, and they run on Node 22.13. All five are used now: `state` and `view` throughout, `autocomplete` for completion, `language` for folding, and `lint` for lint. `@codemirror/language` depends on `@lezer/*` packages, which nothing in Drafter calls.
- **2026-10-25** — **Enter in a heading or transition inserts two line breaks only at the line's end.** Technical design §3.3 says Enter in a scene heading or a transition inserts `\n\n`, since a heading is always followed by a blank line. Taken for the whole line, that would also split a heading in two when Enter is pressed in the middle of it, with a blank line between the halves. So the two breaks go in only when the cursor is at the end of the line. In the middle of it, and for a selection, Enter is an ordinary line break. What counts as a heading or a transition is what the parse says: a lower-case `int. hall - day` alone in its paragraph, `CUT TO:`, and `>FADE OUT.` count, and a line that only opens like a heading in the middle of an action paragraph does not. If a blank line already follows the heading, the two breaks still go in, and the cursor lands in a new paragraph between the heading and that blank line.
- **2026-10-25** — **Enter moves past a parenthetical's `)` only from just before it.** The table says the cursor moves past the `)` and then a break goes in. That happens when the cursor is in a `parenthetical` block and the rest of its line is exactly `)`. Anywhere else in the parenthetical, Enter splits the line like any other, and after the `)` it is an ordinary break.
- **2026-10-25** — **Enter inserts `state.lineBreak`, never indents, and handles every cursor.** The file's own break goes in (`\r\n` for a CRLF file, set with `EditorState.lineSeparator`), and a break is one position whatever its length, so each cursor ends one position past its break. Nothing is copied from the line above, because a line of spaces changes how the lines around it are read (technical design §2.5). Enter works out every cursor's change itself, with the new cursors from a running total, in one pass. `changeByRange` maps each range's changes through the ones before it, which is quadratic in the number of cursors.
- **2026-10-25** — **Cue mode ends at Enter, when the cursor leaves the line, and when the `@` is deleted.** `cueMode` is a field turned on by an effect that only Tab's command sends, so a typed `@` doesn't start it. It then stays on while the main cursor is on the cue's line, so Home, End, and the arrow keys along the line keep it, and it ends when a transaction puts the cursor on another line: Enter, a click, an arrow key up or down, or a paste that holds a line break. The cue's line is followed through each transaction (its start is mapped through the changes), so text added above it doesn't end cue mode. It also ends when the line no longer opens with `@`, so a writer who undoes a stray Tab by deleting its `@` doesn't find the next words changing case. Once it has ended, going back to the line doesn't turn it on again. The effect, `startCue`, isn't among the package's exports: only the keymap sends it.
- **2026-10-25** — **The input filter changes typing, and only typing.** It rewrites transactions with the user event `input.type`, which is what CodeMirror gives typed text. A paste, a drop, a completion, and a change the app makes (a lint fix, a rename) keep their case, and so does text still being composed by an input method (`input.type.compose`), which can't be changed under the writer without breaking the composition. Only the part of an insertion on the line it starts on is changed, since the rest is on lines below. It is `toUpperCase()` over that text, which works on whole code points. CodeMirror's diff of typed text can hand over half of a surrogate pair with the other half already in the document, so a pair is changed as one, and a letter whose upper case is longer (`ß` to `SS`) takes the cursor with it. The filter returns the typing transaction followed by the fixes, in the positions after it, so the typing's selection, effects, and user event are kept and the letters arrive upper-case in the one transaction that types them. Text already in the document is never touched.
- **2026-10-25** — **A scene heading is where the line's prefix has matched and the parse allows one.** The prefix is rule 11's pattern (`INT`, `EXT`, `EST`, `INT./EXT`, or `I/E`, then a `.` or a space, in either case), tested on the text of the line before the typed text. So `int. ` counts, and it stays as it was typed: only what comes after it is upper-cased. The line must also be somewhere a heading can start, read from the parse: a line being typed on, a scene heading, or the first line of an action block. A line that opens with `Int ` in the middle of a paragraph, in a speech, in a note or a boneyard, or on the title page is left alone. Rule 11's other condition, that the run is one line or the line is all upper case, is not used. So `int. hall` typed on the line above a paragraph gets its upper case, though the parse reads that line as action until the prefix is upper case too.
- **2026-10-25** — **Tab goes back to the browser wherever the table gives it no meaning.** Tab and Shift-Tab are taken only where technical design §3.3 gives them a meaning, so a keyboard user can always Tab out of the editor (WCAG 2.1.2). They are left alone in a scene heading, a transition, centered text, a section, a synopsis, a page break, a lyric, a line of speech or a parenthetical with text, on the title page, in a note or a boneyard, on a line of spaces, on an empty line under anything but a cue or a speech, with a selection or more than one cursor, and in a read-only editor. Tab is also left alone on a cue whose extension isn't `(V.O.)` or `(O.S.)`, and on a cue with no name yet, a bare `@`, where Shift-Tab takes the `@` out again. No binding sets `preventDefault`, so a command that returns false leaves the key to the browser. CodeMirror's own Escape-then-Tab, which skips every keymap for a moment, works as it does everywhere else.
- **2026-10-25** — **A cue just typed counts as a cue under Tab, and the extensions cycle on a cue with speech.** The parser reads a lone upper-case line as action, since a cue needs a line after it (rule 12), so a cue the writer has just typed is no `character` block until it has speech. But Tab on the empty line under it opens a parenthetical, as the table's `MARGARET`⏎ row says. The empty line counts as under a cue when the line above is the only line of its action block and the parser would read it as a cue with a line after it. The editor asks the parser itself, by parsing that line with a line of text after it, so it holds no second set of cue rules. The same question settles `convertToAction` below. For the same reason Tab on a lone `MARGARET` is Tab on action with text, and converts the line to `@MARGARET`; the extensions cycle from none to `(V.O.)` to `(O.S.)` and back to none on a cue with speech. The extension goes after the name and before a dual cue's `^`, and comes out with the space before it. One outside the cycle, such as `(CONT'D)`, or more than one, is left alone. The cursor keeps its place in the text, and goes after an extension added at the cursor.
- **2026-10-25** — **`convertToCharacter` and `convertToAction` are for their own context.** The first is for a line of action with text, the second for the first line of a cue, and each returns false elsewhere, so a menu can offer them. `convertToCharacter` upper-cases the rest of the line and puts `@` where the `!` of forced action was, or at the start of the text after any indentation. `convertToAction` takes off the `@` and lower-cases all but the first letter. The first code point is left as it is, so `@marg` becomes `marg`, and markers, extensions, and a dual cue's `^` are lower-cased with the name (`Margaret (v.o.)`). A name that has no lower case to give, such as `Q`, would still be a cue, so its line gets a `!`: `!Q`. In both the cursor keeps its distance from the end of the line.
- **2026-10-25** — **`forceKind` replaces what the line has and never changes case.** It works on the line of the main cursor. A marker (`.` before a letter or digit, `!`, `@`, `~`, `>`) or a wrapper (`>…<`, or `(…)` when one pair of parentheses closes at the end) is taken off before the new one goes on, so `> THE END <` made a parenthetical is `(THE END)`, and the spaces around the text go with it. A dot followed only by dots (`...and then`) and parentheses that are two groups (`(a) and (b)`) are text. The cursor keeps its place in the text, and from a marker or spaces goes to the start of it. The same kind again changes nothing, and still takes the key.
- **2026-10-25** — **`toggleDual` toggles, and the wraps leave their text selected.** `toggleDual` adds ` ^` to the cue line of the speech the cursor is in, and takes it off again with the space before it. The cursor can be on the cue or in any parenthetical or line of speech under it, but not on the blank line that ends the speech, and a lyric on its own is no speech. Elsewhere it returns false. `Mod-/` and `Mod-Shift-/` wrap each selection, which stays selected, or insert the empty pair with the cursor inside: `[[|]]` or `/*|*/`. They don't look at what is selected, so a selection with a blank line in it makes a note the parser reads as text, which the `unclosed-region` lint rule reports.
- **2026-10-25** — **Each command is one transaction, and the line-level ones act on the main cursor.** A command dispatches once, so it is one step in the history. Its user event is `input`, not `input.type`, so the history never joins it to the typing before or after it. A test applies the inverse of each command's changes, as the history does, and finds the text it started with. Tab, Shift-Tab, `forceKind`, and `toggleDual` read the line of the main selection's head, and Tab and Shift-Tab need it to be a single cursor with nothing selected. With a change made for each of several cursors on one line, the changes would repeat. Enter and the wraps take every range. Nothing is done in a read-only editor. The state must have `parsedDoc`, as for `fountainDecorations`; `fountainInput()` adds it.
- **2026-10-25** — **Typing at many cursors costs the filter a quadratic term, which is left.** CodeMirror maps the selection through the filter's changes, which takes time quadratic in the number of cursors: about 120 ms at 10,000 cursors typing in headings, and 400 ms at 20,000. CodeMirror's own typing at that many cursors is far slower (its `replaceSelection` takes 760 ms at 4,000 cursors, and four times that for each doubling), so the filter is not what limits it, and the filter is not made more complicated to avoid it. The commands are linear: Enter and the wraps take a few tens of milliseconds for 20,000 cursors. A complexity test covers 200,000-character lines, a block of 100,000 lines, a speech of 50,000 lines, and 20,000 cursors.
- **2026-10-25** — **The cue line is read from the text.** The parser reads a cue that is still being typed as action, since rule 12 wants a line after the cue and until a speech is typed there is none. So where the cursor is comes from the text of its line, by the rules of §2.5, and what to offer comes from `parsedDoc`. A cue line is one where the line before is blank or there is none, and the text before the cursor starts with `@` or has two or more letters and none in lower case. Blank is the parser's test: empty or spaces, except a line of exactly two spaces, which joins the lines around it. Only the name has to be upper case, and it ends at the first `(` or `^`, so an extension may be any case, as in `HANS (on the radio)`. A line that starts with `#` or `>`, or with a scene heading's prefix and a space, belongs to its own list and never to the cue line, though `INT. HA` is in capitals too. A line that starts a section (`#`), a synopsis (`=`), or a page break (`===`) counts as blank for the line under it, as the parser starts a new block at each and reads a cue right under one. Two places still differ from the parser, both known limits: a cue under a line that holds only a note or boneyard, which the parser reads through, and a cue directly under a scene heading or a transition, which it reads leniently. The text rule calls those lines not blank, so such a cue gets no completion.
- **2026-10-25** — **A name the cue already spells out is not offered, nor is any list when it is typed in full.** The list opens with its first option selected, and Enter accepts the selected option. With `MARGARET` typed in full and no other match, the list would take the Enter meant for the speech and put in the text that is already there; and with a longer name beside it, `DANNY` after `DAN`, Enter would lengthen the name the writer typed. So when the text typed equals one of the labels, ignoring case, no list opens at all, and the writer types another letter (`DANN`) to reach the longer name. Dropping only the exact match, as the first version did, left `DANNY` selected after `DAN`. Case is ignored: Enter on `@Margaret` beside `MARGARET` would only change the writer's capitals, and `@McCLANE` beside `MCCLANE` should keep its own. The same test applies to every list. The line being typed is never one of the labels: the parser may already read it as a cue, a heading, or a section, and a name would always equal itself, so the labels are read from the parse without the blocks on the cursor's line. Tests: the source gives nothing for the full name in each list, and for `DAN` beside `DANNY`; and a view with CodeMirror's own completion closes the list on the last letter and leaves Enter alone in the instant before it closes.
- **2026-10-25** — **The source filters and ranks, not the library.** The result has `filter: false`, so CodeMirror keeps the options in the order given. Its own matching is fuzzy, so `MARGARET` would offer `ANN MARGARET` and Enter would replace the writer's text with another name, and it sorts options that match equally by their labels, which would lose the ranking. So the source matches the start of the text, ignoring case, and marks that start of each label as matched, for the popup to show (`getMatch`). The cost is that CodeMirror takes no `validFor` with `filter: false`, so the source is asked again after each keystroke, once typing pauses for the library's 100 ms. Each question is one pass over the blocks, about 0.6 ms in a script of 100 KB, and a test asks a hundred times. `fountainCompletion()` is `autocompletion({ override: [fountainCompletionSource] })` with `parsedDoc` added, as `fountainHighlighting()` brings the field; the source itself needs the field in the state, as `fountainDecorations` does.
- **2026-10-25** — **Names go by the last cue before the cursor, then by number of cues.** `characters()` gives the last cue in the whole script, which would put first a name that speaks again further down, so the blocks before the cursor's line are walked once for each name's last cue there. A name with no cue before the cursor comes after those that have one, the most cued first, and ties keep the order of first use. The cue the cursor is on is not before it. Locations go by use, the most used first. For times, transitions, and extensions, the ones the script uses come first, the most used first, and then the stock ones it doesn't use, in the order the design lists them. Section titles are each once, in the order of the script: they are for cross-reference while outlining, so recency has no part in them.
- **2026-10-25** — **When the list opens.** Typing opens it once the text being completed has two characters, and asking (Ctrl+Space) opens it at any length. The text counted is all of what is being completed, from where the name, location, time, transition, title, or extension starts to the cursor, and not the last word, so `OLD M` has five. Asking is also more generous on a cue line: with the line before blank, an empty line, or a single letter without an `@`, is a place for a name, so that Ctrl+Space on a new line lists the cast, where typing needs two letters. An `@` alone is no characters of a name, so after Tab on a blank line, which puts in an `@` and nothing else, the list comes up only if the Tab command asks for it. `fountain()`'s Tab does ask (see below).
- **2026-10-25** — **A name that needs an `@` is offered only after one.** Without an `@` a cue has to pass the parser's test, a capital letter and none in lower case. A name with lower case (`McCLANE`) or with no case at all (a name in Japanese) would not make the line a cue, so completing it onto a line with no `@` would turn the line into action. Such a name is left out unless the line has an `@`, and after an `@` every name is offered.
- **2026-10-25** — **Extensions.** They are offered after a name and a space, and from a `(` that is still open: `(V.O.)`, `(O.S.)`, and the extensions the script uses, each on its own, so a cue with `(V.O.) (SUBTITLED)` gives two. The completion replaces from the last open parenthesis, so a second extension completes as the first does. A name that goes on past the space (`OLD MAN` after `OLD `) is completed first, and extensions are offered after a space only when no name goes on from the text. `(CONT'D)` is offered like any other extension when the script already has one; the stock list leaves it out because the layout adds it (technical design §5.4), and `manual-contd` reports one typed where the layout would.
- **2026-10-25** — **Headings, transitions, and sections.** A scene heading's prefix is the parser's own (`INT.`, `EXT.`, `INT./EXT.`, `I/E`, `EST.`, in any case), and it has to be a word of its own followed by a space: `INTERIOR HA` and `INT.HA` are not headings here. After it, up to the last ` - ` or ` – `, the cursor is in the location, and after that separator it is in the time. The split is the parser's, so the last separator wins and `INT. A - B - NI` completes a time, and a hyphen with no spaces around it is part of the location. A completion starts after the spaces that follow a separator, an `@`, a `>`, or a run of `#`. A heading, a `>` line, and a `#` line need no blank line before them.
- **2026-10-25** — **Ctrl+Space anywhere lists names for the word before the cursor.** Phase 1 design §5.3 has Ctrl+Space bring the list up anywhere. When completion is asked for (`context.explicit`) and the line is in no other context, in action or in a speech, the source offers every name that goes on from the word before the cursor, matched from its start and ignoring case; with no word yet, after a space or at the start of a line, it offers the whole cast. The word is letters, numbers, and apostrophes. This is after the cue-line rules, so a cue line is completed as before, and it is only for asking: typing offers nothing in action. Names are offered as text here, so one that needs an `@` to be a cue (`McCLANE`) is offered without it, since the line is not being made a cue. After a `)` or other punctuation with no word, nothing is offered, so Ctrl+Space after `(V.O.)` stays quiet. The `#`, `>`, and heading lines keep their own lists.
- **2026-10-25** — **Fold ranges.** A section folds from the end of its title line to the end of the last block before the next section of equal or shallower depth, so it holds its deeper sections and its scenes. A scene heading folds to the end of the last block before the next scene heading or section. The fold ends with that block's last line, not with the blank line after it, so scenes folded one after another keep their gap. A heading with nothing under it has no fold, and no other line does: the title page has none, and the `/* drafter */` metadata block, which belongs to no scene, is left out of the last scene's fold. The ends are worked out for the whole script in one pass over the blocks, with a stack of the open folds, and kept for that parse, so each query costs a binary search. `foldService` asks only for the heading's own line.
- **2026-10-25** — **What a folded scene shows.** Its heading, and after it an ellipsis and the first synopsis inside the scene (`INT. HALL - DAY… Margaret finds the letter.`). A folded section shows its title and an ellipsis, with no synopsis, since the scenes it holds would offer one each. The placeholder is built with `textContent`, never `innerHTML`, and keeps CodeMirror's `cm-foldPlaceholder` class, title, and aria-label. The synopsis is read when the fold is made, so it is not refreshed until the scene is folded again, which is when its text is out of reach anyway. `fountainFolding()` brings `codeFolding` with this placeholder, and two `codeFolding` configurations with different placeholders conflict, so an app adds `foldGutter` and the fold keys and not its own `codeFolding`.
- **2026-10-25** — **The cursor's element on a blank line and on the title page.** `cursorElement` is null on a blank line, and on any line the parse puts in no block: empty, or spaces. A line of exactly two spaces inside a speech is a line of that speech, as the parser reads it, so it is an element, with the speech's index. The title page is `blockIndex` -1 and `kind` `'title_page'`, with `lineIndex` counting its lines from 0, continuation lines included. `lineIndex` is a difference of line numbers, so it is the line's place in the block, and one binary search finds the block. `onCursorElement` calls back when the three fields change, on a move or an edit, and not for the element the cursor starts in, which the app reads with `cursorElement`; so it doesn't run before the app has the view. An edit above shifts `blockIndex`, which is reported.
- **2026-10-25** — **A fix applies only to the text that was linted.** CodeMirror maps a diagnostic's range through the edits made in the linter's 300 ms delay, but a fix's changes are offsets into the linted text, so applying them later could change the wrong characters. `fountainLint` builds its actions with the `Doc` it linted, and an action applies its changes only while `view.state.field(parsedDoc)` is that same `Doc`. Otherwise it calls `forceLinting(view)` and changes nothing, and the writer chooses the fix again from the new result. Undoing back to the same text is a new parse, so it is refused too. `toCodeMirror(diagnostics)` keeps its plain signature and makes unguarded actions; `fountainLint` is where the `Doc` is known. (`forceLinting` acts only when a lint is due, which any change to the text arranges; see the entry on `relint`.)
- **2026-10-25** — **`relint(view)` lints on demand, and a fix keeps the editor's line break.** In `@codemirror/lint` 6.9.x, `forceLinting` runs only a lint that is already pending, and one becomes pending after a text change, a reconfigure of the linter, or `needsRefresh`. A change to what `template()` or `options()` returns is none of these, so Strict Fountain switched on changed nothing until the next keystroke. `fountainLint` gives `linter` a `needsRefresh` that is true for a transaction carrying a private effect, and `relint(view)` dispatches that effect and then calls `forceLinting`. The app calls `relint` after changing the template or the options. A fix's changes come from a parse that reads every line break as `\n`; the action replaces each `\r?\n` in an insert with `state.lineBreak` before it dispatches, since CodeMirror splits a line only at its own break and a bare `\n` in a CRLF editor would sit inside a line. Tests: the severity changes after `relint` with no edit; and under `lineSeparator` `\r\n`, "Insert a blank line" adds a real line and the text has `\r\n\r\n`.
- **2026-10-25** — **Tab starts the name list.** Phase 1 design §5.3 has names come up after Tab on a blank line. `fountainTab` puts in an `@` and turns on cue mode, which is too little for the completion to open on its own, so `fountain()` binds Tab to a command that runs `fountainTab` and, if that transaction carried `startCue`, calls `startCompletion`. The source then lists the whole cast for the `@`. A Tab that does anything else, such as cycling an extension, or that is not handled, opens nothing. `fountainKeymap` itself is unchanged, so an app that builds its own keymap from it does not get the list.
- **2026-10-25** — **`fountain()` adds lint only with a template.** Lint needs a template, so `fountain({ template })` adds `fountainLint`, with `lintOptions` for its options, and `fountain()` alone has no lint and no gutter. `onCursorElement` adds the callback. `fountain` is in `src/fountain.ts`, and `index.ts` stays a list of exports.
- **2026-10-25** — **A note or boneyard typed on a heading or cue line is left as typed.** The upper-casing filter is for the heading and the name, and a note after them is the writer's own words. While a `[[` or `/*` is open the parse has no region for it, so the filter reads the line before the cursor for the last opener with no closer after it, and also asks the parse whether the position is inside a note or boneyard that is closed or runs to the end. In either case nothing is changed. Typing goes back to upper case after the closer, so `INT. hall [[check it]] now` is `INT. HALL [[check it]] NOW`.
- **2026-10-25** — **`forceKind` keeps a byte-order mark.** `trim` counts U+FEFF as space, so the command took off the BOM at the start of a file along with the spaces. It now leaves a BOM at the start of the line out of the line's text and replaces only what follows, and the cursor's place is counted from there. The spaces around the text still go with the marker, as above.

Panels take focus (`tabindex="0"`), because they scroll and hold nothing else focusable.
- **2026-10-25** — **Nuxt UI's palettes are amber and zinc,** its closest built-in ones. Drafter's exact colors come from `assets/css/tokens.css`, and `test/tokens.test.ts` holds every text color in it to WCAG contrast.

Then the CSP step and Netlify's publish directory find nothing. `nuxt.config.ts` pins `static`, so local and Netlify builds are identical.
  - `pnpm e2e` deletes `.output` first and builds with `NETLIFY=true`, so the browser tests go through Netlify's preset selection.
  - Without the deletion, a stale `.output/public` from an earlier build hid the failure.

The width tests load the page at 320 and 360 pixels and compare the page's width with the root's client width. Under mobile emulation, `innerWidth` grows to fit whatever overflows, so it can't show overflow. Below 400px the toolbar shows the square mark instead of the wordmark, which keeps it within 320px (WCAG 1.4.10).

- **2026-10-26** — **One editor, kept in module state.** `useEditor()` (`app/editor/session.ts`) creates the `EditorView` once, on first use in the browser, and keeps it for the visit, with the parse, the cursor's element, and the template as shallow refs. - **2026-10-26** — **The Drafter packages resolve to their source through a Vite alias,** set in `nuxt.config.ts` as `vite.resolve.alias`: one regular expression that matches exactly `@drafter/<name>` for the six browser-side packages and points at `packages/<name>/src/index.ts`. It covers the client, the server bundle, and the layout worker, and the build passes with every package's `dist/` removed. A subpath such as `@drafter/render-html/style.css` isn't matched and resolves as usual. That test reads the outline of the `.cm-editor` around the focused text.

- **2026-10-26** — **Revert to Saved is one change in the editor's history, and writes nothing.** `revertToSaved` replaces only the part of the text that differs from the text last saved (the session's baseline), so the cursor, the folds, and the scroll stay where they are, as a single transaction isolated from the typing before it (`isolateHistory`), so one undo brings every change back and redo reverts again. It is available while the script has changes (`dirty`), the file's saved text is known, the script's kind is still its file's (after a change of kind the saved text is the other kind's, and Save would act as Save As), and the editor is not locked (a tab that only shows the script, a switch under way, a file that can't be checked). A sample and a script never saved have no saved text, so there is nothing to revert. The message names the file, goes to a polite live region (`role="status"`, `aria-live="polite"`) and to a toast that empties after eight seconds (`timedSay` in `storage/say.ts`, now shared with the export toast).

- **2026-10-26** — **A module's id is a name, not free text.** `ScriptModule.id` must be lowercase letters and digits joined by single hyphens (`script-doctor`), as must a tab's `id`. The id is a settings key (`module:<id>:<key>`), an element id, and part of the tab's id (`module-<id>--<tab>`, whose double hyphen can't occur in an id, so two modules' tabs can't meet); a colon or a space in it would break one of the three. - **2026-10-26** — **Two modules with one id fail the build, and the app skips the second if one gets through.** `scripts/modules.mjs` reads each `modules/*/index.ts` before the build and throws, naming both folders, when two declare the same id. - **2026-10-26** — **The host keeps what a module does in settings rows with fixed names.** Which modules are on is one row, `modules:enabled`, a list of ids, so a module can't turn itself on by writing a key of its own; a module's storage is `module:<id>:<key>`, and the colon-free id keeps one module's prefix from being another's. - **2026-10-26** — **A module's commands are listed under its name, and have no keys.** The host registers them as `module:<id>:<id>` with the module's name as their group and its icon, so the palette (which draws a group for each name it finds, after the five) shows them as a block, and turning the module off takes them out by id (`unregisterCommands`). Their `keys` and `global` are not carried over: the registry binds `global` keys on the whole page in the capture phase, and a module that could take Mod+S would break saving. A command's `enabled` that throws counts as off. Every `run` goes through the same guard as the toolbar button.
- **2026-10-26** — **A module on adds its button, tab, and commands; off takes them away, and the tab is closed where it was open.** The button and tab are computed from which modules are on; the commands are registered by `startModules` as the list changes. - **2026-10-26** — **Module problems are mapped through every edit.** A module sets its problems once, against the text as it was; an edit above would leave their lines wrong. The host keeps them as positions and maps each through the edit's `ChangeSet` (new `onChange` on the session, which also says when the text was replaced wholesale). An item whose whole text an edit replaced is dropped (the fix that was applied, for one); one whose text an edit touched stays, without its fix, which was written for the old text; the rest move with their text, fix included. All go when another script is opened. This keeps a fix from ever applying to text it wasn't made for, the guard cm-fountain's own fixes have.
- **2026-10-26** — **A change from a module is one undo step of its own.** `applyChanges` (and a module problem's fix) go through `applyTextChanges`: positions are checked (inside the text, not backwards, not overlapping; otherwise it throws and changes nothing), inserted line breaks become the editor's own, and the transaction is `userEvent: 'input'` with `isolateHistory('full')`, so one Mod+Z reverses exactly the module's change and never takes the writer's typing with it. In a tab that only shows the script it does nothing and says so with a toast.
